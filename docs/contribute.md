# Разработчикам

Проект открыт: форкайте, добавляйте свои типы иллюстраций и виды заданий.
Устройство подробно — в [архитектуре](architecture.md), принципы схемы
данных — в [принципах](schema-design-principles.md); ниже только то, что
нужно, чтобы начать.

## Запуск

```bash
git clone <репозиторий> && cd physics-skill
pip install -e ".[dev,docs]"
python -m pytest tests -q          # тесты
python tools/dev.py                # живой просмотр иллюстраций и примера
```

Пакет `physics_svg` зависимостей не имеет и не должен их заводить: скилл
обязан работать офлайн, без pip и без сети. Это проверяется тестом, который
сверяет импорты собранного бандла со списком стандартной библиотеки.

## Слои

```
draw/       холст, геометрия, трансформации, стили. Про физику не знает.
elements/   физический словарь: шкалы, штриховка, уровни жидкости.
schema/     ядро валидации на dataclass + аннотациях, JSON Schema.
visuals/    библиотека иллюстраций: одна папка = один тип.
document/   блоки, виды заданий, нумерация, «Ответы», HTML.
```

Зависимости строго вниз. Иллюстрация рисуется **элементами**, а не строками
SVG: если в новом типе появляется `f'<line x1=...'`, скорее всего нужного
элемента просто ещё нет — заведите его в `elements/`.

## Новый тип иллюстрации

Одна папка:

```
src/physics_svg/visuals/<тип>/
  model.py      dataclass-спека и её инварианты
  render.py     (model, canvas) -> рисует элементами
  specs/*.json  примеры
  doc.md        справочник для модели: поля, правила, JSON
  card.md       карточка для учителя: что это и что сказать Claude
```

Регистрация — в `__init__.py` папки. Больше **нигде** ничего править не
нужно: союз типов для валидации, JSON Schema, галерея на сайте,
golden-тесты, справочник в бандле и библиотека заготовок собираются из
реестра.

`tests/visuals/test_conformance.py` проверит за вас, что тип принёс всё
обещанное, что каждая спека рендерится, укладывается в свою рамку,
детерминирована и экранирует авторский текст.

## Новый вид задания

То же самое в `src/physics_svg/document/questions/`: модуль со спекой и
парой рендеров, рядом `<тип>.md` и `<тип>.card.md`. Второй рендер отдаёт не
готовую разметку, а **форму ответа** — `Inline` (короткая строка), `Rows`
(строка на элемент), `Block` (чертёж) или `None`, если ответа нет вовсе;
вёрстку выбирает секция «Ответы».

Если ученик выбирает из готового набора — вариантов, столбца, групп, банка
слов — не пишите своих проверок: спроецируйте своё поле на `Domain`
(`document/domain.py`). Оттуда берутся уникальность значений, принадлежность
инлайн-ответа набору и предел на буквенные метки, а лишнее значение
автоматически значит «дистрактор» — тем же словом, что и у остальных видов.

Пример JSON из справочника **и есть** фикстура тестов — он рендерится,
проверяется на эскейпинг и попадает на сайт. Поэтому пример должен быть
рабочим, а не иллюстративным: это целое задание (`task`) с условием, самим
вопросом и местом под запись — то, что учитель получит на листе. Блоков
```json в справочнике может быть несколько, на сайт попадут все.

В `register(...)` есть `order` — место вида на странице сайта и в индексе
справочника, кратное десяти. Порядок задаёт человек: он идёт по тому, как
часто вид нужен, а не по алфавиту латинского тега.

Перед тем как проектировать поля, прочитайте
[принципы схемы](schema-design-principles.md): ответ живёт инлайн рядом со
своим содержимым, раскладка не живёт в вопросе, нумерация и баллы — на
контейнерах.

## Проверки перед коммитом

```bash
python -m pytest tests -q
python -m ruff check . && python -m mypy
python tools/build_skill.py        # бандл собирается, SKILL.md ничего не врёт
python tools/build_site.py && zensical build --clean --strict
```

Если рендер изменился намеренно — пересоздайте эталоны
(`REGEN_GOLDEN=1 python -m pytest tests -q`) и **просмотрите диф глазами**.
Тест ловит изменение, но не отвечает на вопрос, стало ли лучше.

## Ветки

**`main` — это то, что у учителя.** Каждый push в неё пересобирает сайт и
кладёт на него свежий архив скилла, а страница установки ведёт именно на
него. Поэтому `main` двигается только при выпуске.

**`next` — разработка.** Там коммиты, короткие ветки под рискованные правки
и метка `X.Y.Z+dev`, которую никто не скачивает. CI гоняется на всех ветках,
так что `next` проверяется полностью.

Отсюда главное свойство: галерея, виды заданий и справочники на сайте всегда
описывают ту же версию, которую учитель держит в руках. Расхождения «на
сайте есть, в скилле нет» не бывает по построению, а не по внимательности.

Исключение — правки, не касающиеся пакета (тексты в `docs/`, README): их
можно пускать прямо в `main`. Сайт обновится, архив останется прежним,
потому что код не изменился.

## Публикация

Ничего вручную выкладывать не нужно. **Тег `vX.Y.Z`** выпускает версию:
прогоняются проверки, собирается бандл, создаётся GitHub Release с архивом
и разделом из `CHANGELOG.md`.

Порядок выпуска:

```bash
git switch main && git merge --ff-only next
python tools/release.py 0.3.0
git push --follow-tags
git switch next && git merge --ff-only main
python tools/release.py --next
```

`release.py` поднимает номер в `src/physics_svg/__init__.py` — единственном
месте, где он записан, — переименовывает «Не выпущено» в раздел с сегодняшней
датой, коммитит и ставит тег. Второй вызов помечает `next` как «не выпуск»,
и делается он на `next`: такой метке на сайте делать нечего. Пуш скрипт не
делает, публикация остаётся осознанным действием.

Номер выбирается по накопленному разделу «Не выпущено»: одни исправления —
патч (`0.2.1`), появилось то, чего учитель раньше попросить не мог, — минор
(`0.3.0`). Это ровно то различие, которое описано в шапке `CHANGELOG.md`, и
читает его учитель, а не разработчик.

**Размер выпуска выбирается один раз — при выпуске.** Открытие цикла об этом
не спрашивает и спросить не может: цикл открывается раньше работы, которая
решит, патч это или минор. Поэтому `next` носит метку вида `0.2.1+dev` —
«после 0.2.1, но не выпуск» (локальная версия по PEP 440). Она называет
выпуск **позади** себя, а не впереди, и ничего не обещает: из `0.2.1+dev`
одинаково доступны `0.2.2`, `0.3.0` и `1.0.0`. Назад не пускает только
последний тег.

Оба режима требуют, чтобы соседняя ветка была влита. Разъехавшиеся `main` и
`next` — единственный способ сломать эту схему молча: выпуск без работы или
новый цикл без выпуска.

Тег, не совпадающий с версией пакета, и отсутствующий раздел в
`CHANGELOG.md` роняют выпуск до публикации — архив, чей `VERSION` врёт,
потом не сопоставить с багом.

Предвыпусков не делаем: пока проект не дошёл до `1.0`, ноль в старшем
разряде сам означает «может ломаться». Показать сборку до выпуска проще
локально — `python tools/build_skill.py` кладёт архив в `dist/skill/`, его
можно загрузить в Claude или передать одному человеку, ничего не публикуя.
Если предвыпуск всё же понадобится, тег по PEP 440 (`1.1.0rc1`) на ветке
`next` выложится с `--prerelease` и не займёт «Latest release».

Пишите изменения **для учителя**: что теперь можно попросить и что стало
правильнее, а не какие функции переименованы. Этот же текст читают в
релизе.

И буквально: раздел версии тянется до следующего `##`, поэтому в
`CHANGELOG.md` всё, что относится к файлу целиком — формат, что версия
значит для учителя, откуда начинается история, — живёт в шапке, выше
первого `##`. Приписанное в конец файла попадёт в заметки последнего
выпуска (это проверяет `tests/test_release_notes.py`).

## Язык

Код и комментарии — английский. Сообщения об ошибках, справочники и сайт —
русский: их читают учитель и модель, а не контрибьютор.
