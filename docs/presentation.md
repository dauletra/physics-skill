# Презентация к уроку

План третьего артефакта скилла. Документ (HTML/Word) остаётся как есть;
презентация — **отдельный жанр со своей схемой**, а не режим документа.
Общее у них — иллюстрации, конвенции авторского текста и ядро валидации.

Документ — проектный: целевое устройство, зафиксированные решения, фазы.
Читать вместе с [архитектурой](architecture.md) и
[принципами схемы](schema-design-principles.md).

Статус: **П1–П3 сделаны** — инлайн общий, схема и реестр слайдов живут,
`physics-svg present` собирает плеер с данными. Впереди П4 (полный словарь
и интерактив) и П5 (поверхность скилла).

## 1. Задача

Учителю к уроку нужен не только лист, но и презентация: тема, цели,
объяснение новой темы, задачи для доски, рефлексия. Содержимое презентации
**не пересекается** с содержимым листа — это разные педагогические жанры с
разными целями. Пересекаются только иллюстрации: график из `visuals/`
одинаково нужен и на слайде, и в задании.

Показывает презентацию не PowerPoint, а собственный плеер: HTML-JS шаблон,
который сегодня живёт в репозитории и вкладывается в один самодостаточный
файл, а в будущем переедет на отдельный сервер (платформа с базой данных и
электронным журналом; материалы туда будет загружать MCP-сервер). Поэтому
главное проектное требование: **данные и плеер развиваются параллельно, но
отдельно**, и граница между ними — контракт `presentation.json`.

## 2. Целевая картина

```
                         ┌─ output/presentation.json   канонические данные
слайды -> модель ────────┤
 (spec)   (presentation) └─ output/presentation.html   плеер + те же данные,
                                                       вложенные блобом
```

Сегодня оба артефакта собирает скилл офлайн. Завтра, с появлением сервера,
меняется только транспорт: вместо «вложить JSON в шаблон» — «загрузить JSON
на сервер». Контент, схема и валидатор не меняются вовсе. Это возможно,
только если уже сегодня держится дисциплина из §4: плеер рендерит из JSON в
рантайме, Python разметку слайдов не пишет.

Слои и зависимости — по образцу документа:

```
presentation -> visuals -> elements -> draw
presentation -> schema
presentation -> inline (общий разбор авторского текста, §6)
```

`presentation/` и `document/` друг друга **не импортируют**. Проверяется
тем же способом, что и остальные границы слоёв.

## 3. Зафиксированные решения

| решение | выбор | почему |
|---|---|---|
| место в архитектуре | сосед `document/`, не его режим | жанры не пересекаются по содержимому; общее (иллюстрации, инлайн, валидация) лежит ниже обоих |
| продукт сборки | `presentation.json` + `presentation.html` из одного источника | JSON — канон и будущий груз для сервера; HTML — сегодняшний способ показать без сервера |
| кто пишет разметку слайдов | **только JS-плеер, в рантайме** | Python инжектит блоб и не интерполирует контент в HTML — иначе при переезде на сервер появится второй рендерер, и они разъедутся |
| извлекаемость | JSON лежит в HTML целым блоком `<script type="application/json">` | тот же приём, что черновик в `document.html`; миграция уже отданных файлов — «достать блоб и загрузить» |
| версия контракта | поле `format` (целое) в корне JSON, с первого дня | сервер будет получать файлы от скиллов разных версий; без номера не отличить «старый формат» от «битый файл» |
| авторский текст | приходит в JSON **разобранным в прогоны** (§6) | конвенции `$…$`/`<sup>`/подчёркиваний — одни на весь скилл; плеер маппит прогоны на span и KaTeX и никогда не парсит |
| иллюстрации | спека визуала инлайн в слайде; сборка рендерит и кладёт в JSON готовый SVG рядом со спекой | тот же валидатор и та же библиотека заготовок, что в документе; плеер вставляет SVG как есть, сервер сможет перерендерить из спеки |
| интерактивность | в JSON — смысл, поведение — в плеере | слайд несёт `answer`, но не «показывать по клику»; переделка интерактива не трогает ни схему, ни сохранённые уроки |
| плеер в репозитории | статические файлы без шага сборки | у скилла нет npm и нет сети; плеер на фреймворке возможен только как вендоренный собранный бандл, и пока он прост — vanilla JS |
| KaTeX | с CDN, как в документе | тот же осознанный компромисс; формулы на слайдах без интернета не отрисуются — если станет больно, это решит сервер, а не офлайн-фолбэк |
| цвет | иллюстрации остаются ч/б; тема слайда — дело плеера | решение «цвет автору недоступен» не пересматривается; фон и акценты — CSS плеера |
| верх документа | плоский список слайдов | у линейной презентации нет смысловой вложенности; этап урока — слайд-разделитель `section`, а не контейнер (раскладка не меняет смысл — принцип 8) |
| PowerPoint | не делаем | решено после сравнения: плеер выбран ради интерактива и будущей платформы; pptx-бэкенд возможен позже как ещё один эмиттер той же схемы, обещаний о нём нет |

## 4. Контракт `presentation.json`

Корень:

```json
{
  "format": 1,
  "title": "Равноускоренное движение",
  "slides": [ ... ]
}
```

* `format` — версия контракта данных, меняется только при ломающем
  изменении формы JSON (не при добавлении типа слайда: неизвестный тип
  плеер обязан показать заглушкой с именем типа, а не упасть).
* `title` — название урока; плеер ставит его в `<title>` и на титул, если
  автор не дал слайда `title`.
* `slides` — плоский список; порядок = порядок показа.

Каждый слайд: `{"type": …, поля вида}` — тот же конверт, что у блоков
документа. Поля с авторским текстом приходят в **эмитированном** JSON
разобранными в прогоны (§6); в **авторском** JSON (черновике) они —
обычные строки. Это различие такое же, как между `blocks/*.json` и
готовым `document.html`: черновик пишет модель, канон собирает скилл.

Иллюстрация в эмитированном JSON:

```json
"visual": {
  "spec": { "type": "graph", ... },
  "svg": "<svg …>…</svg>",
  "width": 490, "height": 320
}
```

`spec` — то, что написал автор (по нему сервер сможет перерендерить или
дать отредактировать); `svg` — то, что показывает плеер; размеры — чтобы
плеер резервировал место до вставки.

## 5. Словарь слайдов v1

Реестр по образцу `document/questions/`: один слайд = один модуль +
`<тип>.md` (справочник для модели, пример — целый слайд) + `<тип>.card.md`
(карточка для учителя), `register(order=…)`. Конформанс-тест от реестра —
зеркало `test_questions.py`.

| type | поля | зачем |
|---|---|---|
| `title` | `text`, `subtitle?` | открытие урока: тема, класс/предмет |
| `objectives` | `items[]` | цели урока, «сегодня научимся…» |
| `content` | `heading?`, `text?`, `items?`, `visual?` | объяснение темы; рабочая лошадка. Хотя бы одно из `text`/`items`/`visual` — слайд не печатает пустоту |
| `example` | `text`, `steps[]`, `answer?`, `visual?` | разбор у доски; плеер вправе раскрывать шаги по одному |
| `board_task` | `text`, `visual?`, `answer?` | задача для ученика у доски; `answer` — для учителя, когда показывать — решает плеер |
| `prompt` | `items[]` | вопросы классу, фронтальный опрос |
| `reflection` | `items[]` | рефлексия в конце урока |
| `section` | `text` | разделитель этапов урока; плеер может строить по ним навигацию |

Пять решений, общих для всех слайдов:

* `board_task` — **не** `open` из документа: у него нет поверхности
  письменного ответа, нумерации листа и секции «Ответы». Жанры не
  заимствуют виды друг у друга.
* Ответ живёт инлайн в своём слайде (`answer` рядом с условием) — принцип 5
  схемы действует и здесь.
* Никакой раскладки в схеме: слайд говорит «условие + визуал», где визуал —
  справа или снизу — решает плеер (принцип 10).
* Нумерации слайдов в данных нет: номер — позиция в списке, как номер
  задания в документе (принцип 2).
* Общего с листом хранилища визуалов нет: график, нужный и там и там,
  повторяется в двух черновиках. Дешевле редкого дублирования — только
  прямота; вернуться к вопросу, если дублирование станет реальной болью.

## 6. Общий инлайн — подъём `document/inline.py`

Разбор `$…$`, `<sup>/<sub>` и подчёркиваний должен быть один на весь скилл:
учитель не обязан помнить, что в листе формула пишется так, а на слайде
иначе. Сейчас `parse_inline` и типы прогонов (`Run`, `Math`, `Blank`,
`Text`) живут в `document/`; презентации импортировать их оттуда нельзя
(§2), значит они поднимаются на уровень пакета — единственный перенос
существующего кода во всём плане.

* Новый модуль уровня пакета несёт типы прогонов, `parse_inline` и
  `math_spans`. `document/layout.py` импортирует типы оттуда;
  документные инлайн-элементы (`Gap`, `Slot`, `Square`, `Verdict`) —
  вёрстка листа, они остаются в `layout.py`.
* Вывод HTML и Word не меняется ни на байт — рефакторинг идёт под
  существующими golden'ами, как Ф1 Word-экспорта.
* Там же фиксируется **JSON-форма прогона** — часть контракта §4:

```json
[{ "t": "При " }, { "math": "v = v_0 + at" }, { "t": " путь…" }]
[{ "t": "x", "script": "sub" }]
[{ "math": "\\frac{v^2}{2a}", "display": true }]
[{ "blank": 5 }]
```

`blank` на слайде легального применения пока не имеет (подчёркивания в
тексте слайда остаются литеральными, `parse_inline(…, blanks=False)`), но
форма объявляется сразу: она общая, а не презентационная.

## 7. Плеер — `src/physics_svg/presentation/player/`

Статические файлы: страница-шаблон, `player.js`, `player.css`. Правила:

* **Рендер только из JSON.** Плеер читает блоб из
  `<script type="application/json" id="presentation-data">` и строит DOM.
  В шаблоне нет ни одного содержательного тега; сборка делает ровно одну
  замену — вставляет блоб.
* **Неизвестный тип слайда — заглушка с именем типа**, а не падение:
  старый плеер обязан пережить новый тип (это и есть смысл политики
  `format`: номер растёт только на ломающей форме, не на новом типе).
* **Интерактив — собственность плеера**: раскрытие ответа, пошаговый показ
  `steps`, навигация по `section` — всё это его решения, свободно
  меняющиеся без правок схемы.
* Формулы: прогоны `math` рендерит KaTeX с CDN; защита
  `if (window.katex)` — та же, что в документе: без сети формула видна
  исходным текстом, страница не падает.
* Плеер уезжает в бандл как статические файлы; `test_bundle.py` собирает
  презентацию в чистом окружении так же, как собирает документ.

Чем плеер **не** является: он не редактор и не источник правды. Правки —
словами в сессии, пересборка — скиллом; черновик для продолжения работы —
авторские JSON-файлы, а не `presentation.html`.

## 8. Черновик и CLI

Черновик презентации — папка, зеркальная документной:

```
<lesson>/
  presentation.json     манифест: title, order (список имён слайдов)
  slides/*.json         по слайду на файл
```

По файлу на слайд — по той же причине, что по файлу на блок: «переделай
третий слайд» — правка одного маленького файла. Урок с листом и
презентацией — одна папка с двумя черновиками; они не ссылаются друг на
друга.

CLI — новая подкоманда:

```
physics-svg present <lesson>            output/presentation.html + presentation.json
physics-svg present <lesson> -o DIR
```

Ошибки валидации — тем же плоским списком с путями, что у `build`: все
проблемы черновика за один проход.

## 9. Проверки

| что | как |
|---|---|
| граница слоёв | тест: `presentation/` не импортирует `document/` и наоборот |
| HTML/Word документа не изменились | существующие golden'ы держат подъём инлайна (П1) — байт в байт |
| каждый тип слайда | конформанс от реестра: пример из `<тип>.md` собирается, модуль принёс `md`/`card.md`, слайд в минимальной форме не пуст |
| эскейпинг | фузз `PAYLOAD` по всем строковым полям слайдов — через JSON-гейт и через блоб в HTML (закрывающий `</script>` внутри блоба обязан быть обезврежен) |
| канон | golden `presentation.json` примера урока; сборка детерминирована |
| извлекаемость | тест достаёт блоб из собранного `presentation.html` и сверяет с каноническим JSON — инвариант, а не обещание |
| плеер жив | смоук: шаблон содержит точку инжекта, ссылки на свои файлы существуют; поведенческие проверки плеера — глазами (`evals/presentation.md`, чек-лист по образцу `evals/word.md`) |
| бандл | `test_bundle.py`: `present` отрабатывает в чистом окружении, импорты — stdlib |
| сайт | карточки слайдов попадают в галерею; страница вне `nav` роняет сборку — как для типов |

Автотесты не заменяют глаз: «JSON корректен» не значит «слайд выглядит
как задуманo». Один проход по `evals/presentation.md` в браузере — на
каждой фазе, где менялся плеер.

## 10. Фазы

| фаза | содержание | результат | статус |
|---|---|---|---|
| **П0** | этот документ | решения зафиксированы | готово |
| **П1** | общий инлайн: подъём `parse_inline` и типов прогонов на уровень пакета; JSON-форма прогона | вывод документа байт в байт прежний; контракт прогона объявлен | готово |
| **П2** | `presentation/`: манифест, реестр слайдов, загрузчик черновика; типы `title`, `objectives`, `content`, `board_task`; конформанс-тесты | схема живёт, черновик валидируется с точными путями ошибок | готово |
| **П3** | эмиттер `presentation.json`; плеер-скелет (титул, контент, задача — без интерактива); инжект блоба; `physics-svg present`; golden + тест извлекаемости | `present` отдаёт рабочий HTML: открыл — листаешь урок | готово |
| **П4** | типы `example`, `prompt`, `reflection`, `section`; интерактив плеера: шаги, ответ, навигация по этапам | полный словарь v1 | |
| **П5** | поверхность скилла: SKILL.md (когда собирать презентацию, что сказать), `references/slides.md` из реестра, бандл, пример урока в `examples/` (лист + презентация одной темы), страницы сайта | выпуск: учитель получает презентацию | |

Порядок жёсткий только в начале: П1 → П2 → П3 (инлайн нужен схеме, схема —
эмиттеру). П4 и П5 можно резать на выпуски.

Совершенствование плеера после П5 — **параллельная дорожка без фаз**: пока
контракт §4 не ломается, правки плеера — обычные коммиты, не требующие ни
правок схемы, ни пересборки старых уроков (старые файлы несут старый плеер —
это нормально: пересборка обновляет).

## 11. За горизонтом плана

Сервер, база, электронный журнал и MCP-сервер загрузки — сознательно **вне
этого плана**. Всё, что им нужно от нас, план уже даёт: стабильный,
версионированный (`format`), извлекаемый из HTML JSON с разобранными
прогонами и спеками визуалов внутри. Единственное обязательство настоящего
перед будущим — не нарушать §4.

## 12. Риски

| риск | что делаем |
|---|---|
| Python «для простоты» начнёт писать разметку слайда | правило одно и проверяемое: шаблон не содержит содержательных тегов, сборка делает одну замену; ревью держит границу так же, как «разметку пишет только бэкенд» |
| контракт разъедется с плеером | сегодня они едут в одном файле и одном репо — рассинхрон невозможен по построению; политика `format` (§4) заготовлена на момент, когда это перестанет быть правдой |
| `</script>` в авторском тексте рвёт блоб | экранирование в точке инжекта + фузз (§9) — тот же класс защиты, что `draw.clean` |
| плеер потянет фреймворк и шаг сборки | решение §3: статические файлы; фреймворк — только вендоренным бандлом, и только когда vanilla JS реально перестанет справляться |
| словарь слайдов расползётся на «слайд под каждый приём» | тот же тормоз, что у вёрстки: тип заводится под первый урок, которому он нужен, и `content` покрывает всё, что не имеет собственной формы |
| дублирование графика между листом и слайдом надоест | зафиксировано как осознанный компромисс (§5); пересматривать при реальной боли, решением уровня схемы, а не ссылкой-скорую-руку |

## 13. Чего не делаем

- **Не рендерим слайды в Python** — ни серверного HTML, ни второго
  рендерера. Один рендерер — JS-плеер.
- **Не делаем pptx** — выбор сделан (§3); возможен позже как ещё один
  эмиттер, обещаний нет.
- **Не заводим офлайн-фолбэк KaTeX** — компромисс тот же, что в документе.
- **Не делаем `presentation.html` источником продолжения сессии** —
  черновик = авторские JSON; блоб в HTML — для показа и будущей миграции.
- **Не проектируем сервер и MCP** — см. §11.
- **Не кладём в схему оформление** (шрифты, цвета, позиции) и настройки
  интерактива («раскрывать по клику») — первое дело CSS плеера, второе —
  его логики.
- **Не связываем лист и презентацию ссылками** — два независимых черновика
  в одной папке урока.
