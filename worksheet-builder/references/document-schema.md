# Схема данных документа (v4)

Документ — это `document.json` (манифест) + по одному JSON-файлу на
**верхнеуровневый блок** (`blocks/<id>.json`). Документ может быть
конспектом, объяснением, набором заданий или любой их комбинацией — теория
и задания свободно перемежаются. Задание — **дерево блоков**: контейнеры
задают структуру и нумерацию, листья несут содержимое. Принципы, по которым
устроена схема (и по которым добавляются новые виды блоков), — в
`docs/schema-design-principles.md` репозитория разработки (в бандл скилла
не входит: новые виды блоков добавляет разработчик, не сессия).

```
DocBlock = Heading    // подзаголовок раздела
         | Component  // text | table | graph | list | instrument | paper | answer_line
         | Task       // нумерованное задание: { blocks: Block[] } — только здесь живут вопросы
         | Row        // layout: компоненты/заголовки в одну строку

Block    = Component
         | Question   // open | choice | match | ...  — несёт ответ инлайн
         | Part       // контейнер подзадания: { blocks: Block[] }
         | Row        // layout-контейнер в одну строку
```

Ответы заданий в теле документа **не печатаются** — рендерер собирает их в
секцию «Ответы» в конце (по номеру задания и букве подзадания). Вариант без
этой секции — флаг рендера `--no-answers`, не поле схемы.

## document.json — манифест

```json
{
  "title": "Кинематика: равномерное и равноускоренное движение",
  "header": {
    "subject": "Физика",
    "grade": "9",
    "school": "",
    "date": "",
    "instructions": "Внимательно прочитайте условие каждой задачи."
  },
  "order": ["theory-intro", "task-01", "task-02"]
}
```

- `header` (опционально) — анкета-шапка: строка «Школа/класс … Дата …
  Фамилия Имя …», подзаголовок из `subject`/`grade` и строка-инструкция.
  Нужна самостоятельной работе; у конспекта `header` просто нет — печатается
  только `title`. Пустые `subject`/`grade` не печатаются в подзаголовке (без
  висячих разделителей); `school`/`date` пустые — прочерки для заполнения от
  руки рисуются всё равно.
- `order` — порядок верхнеуровневых блоков; имена совпадают с `id` (и именем
  файла) блока, дубли отклоняются валидацией. Если `order` задан, он обязан
  перечислять **все** файлы `blocks/*.json`: файл вне списка — ошибка
  сборки, а не молчаливый пропуск. Несовпадение `id` внутри файла с именем
  файла — тоже ошибка сборки (проверяется в `load_workspace`).

Вся схема (манифест + блоки) проверяется pydantic-моделями
(`worksheet_builder/models.py`) при загрузке: **неизвестное поле — ошибка**
(опечатка не игнорируется молча), неизвестное значение перечисления — ошибка.

Собранный `output/document.html` несёт встроенную копию черновика:
`<script type="application/json" id="document-source">` с
`{"document": …, "blocks": […]}` в конце файла — из одного этого файла
черновик восстанавливается целиком (`document.json` + `blocks/<id>.json`
по `id` блоков). В раздаточном варианте (`--no-answers`) черновика нет —
он раскрыл бы ответы через исходный код страницы.

## Верхнеуровневые блоки (файлы blocks/*.json)

Каждый файл — один блок с обязательным `id`, равным имени файла без
`.json`. Виды:

- **`heading`** — подзаголовок раздела документа:
  `{ "type": "heading", "id": "…", "text": "Основные понятия" }`.
  Внутри заданий заголовков нет — там иерархию рисуют номер и буквы
  подзаданий.
- **Компонент** (`text`/`table`/`graph`/`list`/`instrument`/`paper`/
  `answer_line`) — абзац теории, иллюстрация, таблица вне задания, место
  под работу ученика. Схема — раздел «Компоненты».
- **`task`** — нумерованное задание (раздел «Задание»). **Только внутри
  `task` живут вопросы и `part`** — вопрос на верхнем уровне отклоняется
  валидацией с подсказкой обернуть его в `task`.
- **`row`** — компоненты/заголовки в одну строку (например, прибор и
  пояснение к нему рядом). Задания и вложенные `row` внутри
  верхнеуровневого `row` запрещены.

Нумерация заданий — сквозная по документу в порядке `order`: `task`-блоки
получают 1..N, теория между ними номера не сдвигает.

## Задание (`task`)

```json
{
  "type": "task",
  "id": "task-01",
  "points": 2,
  "blocks": [ ... ]
}
```

- `id` — совпадает с именем файла без `.json` (проверяется при сборке).
- `points` — общий балл задания, печатается в строке номера (`N. (2 б.)`);
  строго больше нуля (проверяется валидацией — ноль баллов всё равно не
  печатался бы). Баллы контейнеров независимы и не суммируются автоматически.
- `blocks` — упорядоченный список блоков; порядок = порядок на странице.

**Инвариант состава** (проверяется при загрузке): на уровне корня `blocks`
содержит либо
- любое число компонентов + **не более одного** `Question` — простое
  задание, без буквы; либо
- любое число компонентов + **один и более** `part` — составное задание.

Смешивать `Question` и `part` как соседей нельзя: на любом уровне списка
роль каждого блока должна быть однозначной. Инвариант считается по
**сплющенному обходу** — `row` прозрачен, его дети считаются соседями на
уровне родителя (см. "`row`" ниже).

**Инвариант условия** (проверяется при загрузке): у каждого вопроса на
пути к корню задания есть хотя бы один блок `text`. Вопрос несёт только
аппарат — варианты, утверждения, оси, пропуски, — а формулировку несёт
соседний `text`; у `open` тело пустое по построению, поэтому без условия
от задания остаётся один номер, а строка в секции «Ответы» всё равно
печатается. Достаточно одного `text` **либо** на уровне задания (он
покрывает все свои `part`), **либо** внутри самого `part`. Условием
считается только `text`: подпись графика, пункты списка и заголовок
таблицы на эту роль не назначаются. Правило действует и для видов,
которые кажутся самообъясняющими: `match` требует «Сопоставьте…»,
`fill_text` — «Вставьте пропущенные слова».

## `part` — подзадание

```json
{ "type": "part", "id": "…", "label": "…", "points": 2, "blocks": [ ... ] }
```

Все поля, кроме `type` и `blocks`, опциональны.

- `blocks` — любое число компонентов + **ровно один** `Question` (по
  сплющенному обходу — внутри допустим `row`). Компоненты внутри `part` —
  контекст именно этого подзадания (условие, своя таблица, свой график);
  компоненты на уровне задания — общий контекст для всех подзаданий.
- **Буквы**: каждый `part` получает букву (`а`, `б`, `в`… — кириллический
  перечислительный ряд, `LETTERS` в `strings.py`) по порядку следования
  среди сиблингов (по сплющенному обходу — `part` внутри `row` получает
  букву так же, как стоящий на уровне задания). Явный `label` побеждает;
  авто-буквы пропускают занятые явно. Явный `label` — одна буква из того же
  ряда `LETTERS` (две системы нумерации в одном документе не смешиваются),
  дубли явных `label` в задании отклоняются валидацией. Буква и `points`
  подзадания (строго больше нуля) печатаются маленькой строкой (`а) (2 б.)`)
  перед содержимым `part`; если ни буквы, ни баллов нет — строки нет.
  Вычисляется при сборке документа (`compute_part_labels` в `document.py`,
  чистая функция), не внутри блока. Та же буква помечает ответ подзадания
  в секции «Ответы» (`3. б)`).
- Вложенный `part` внутри `part` структурно зарезервирован, но пока
  отклоняется валидацией (нумерация глубже одного уровня не определена).

## `row` — блоки в одну строку

```json
{ "type": "row", "id": "…", "blocks": [
    { "type": "part", "blocks": [ ... ] },
    { "type": "part", "blocks": [ ... ] }
] }
```

Layout-контейнер: его дети рендерятся колонками в одной строке и **всегда
делят её поровну** — никаких ширин в данных нет. Влияет **только на
геометрию** — для инвариантов состава и раздачи букв `row` прозрачен: его
дети считаются соседями на уровне родителя, `part` внутри `row` получает
букву в общем порядке.

- Разрешён на верхнем уровне документа (дети — только компоненты и
  `heading`), в `Task.blocks` и в `part.blocks` (там дети — компонент,
  вопрос или `part`); `row` внутри `row` запрещён (зарезервирован).
- `blocks` непустой.
- **Когда использовать.** Только когда блоки действительно должны стоять
  рядом (два подзадания с графиками, две таблицы). Одиночный график в `row`
  не заворачивают: ширина графика и так ограничена дизайн-системой
  (`max-width: 330px` у `svg.visual-svg` — см. `design-system.md`), у него
  единый размер во всём документе.

## `id` на любом блоке

Верхнеуровневый блок обязан иметь `id` = имя файла. Вложенный блок может
иметь опциональный `id` (уникальный внутри задания — проверяется
валидацией; рекомендуется `[a-z0-9-]`). Используется для адресации при
правках и в сообщениях об ошибках валидации; на рендер не влияет.

## Компоненты — чистый контент

Компонент только рисует то, что ему дали. Он ничего не знает про
вопрос/ответ/правильность — никаких `answer`, `correct`-полей
на компонентах не бывает.

```json
{ "type": "text", "body": "Свободный текст." }
```
```json
{ "type": "table", "headers": ["t, с", "υ, м/с"], "rows": [["0", "0"], ["1", "2"]] }
```
```json
{ "type": "graph", "x_label": "t, с", "y_label": "υ, м/с",
  "x_range": [0, 10], "y_range": [0, 20],
  "series": [{ "label": "Тело A", "points": [[0, 0], [5, 10]], "style": "solid" }] }
```
```json
{ "type": "list", "items": ["Не изменяется", "Увеличивается"], "marker": "letter", "columns": "single" }
```
```json
{ "type": "instrument", "kind": "ammeter", "unit": "А",
  "min": 0, "max": 3, "step": 0.1, "value": 1.35, "caption": "Амперметр" }
```
```json
{ "type": "paper", "ruling": "lines", "rows": 4 }
```
```json
{ "type": "paper", "ruling": "mm", "rows": 12, "cols": 12 }
```
```json
{ "type": "answer_line" }
```

- `text.body` — строка; поддерживает `<sup>`/`<sub>` и LaTeX (`$…$`,
  `$$…$$`) как текстовую разметку (см. `references/symbols.md`).
- `table` — настоящая двумерная сетка с подписанными колонками;
  одномерная последовательность пунктов — это `list`, не `table` с пустой
  шапкой. `rows` — `list[list[str]]`, всегда готовые строки.
- `graph.series` — опционально (без него — пустые подписанные оси). Формат
  серии: `{ "label", "points": [[x, y], …], "style": "solid" | "dashed" |
  "dotted" }`, подробности — `references/charts-and-graphs.md`.
  `x_range`/`y_range` — строго `[min, max]` с `min < max` (проверяется
  валидацией).
- `graph.grid` — `"ticks"` (по умолчанию) / `"fine"`: плотность
  координатной сетки. Линии по подписанным делениям есть всегда, `"fine"`
  дробит шаг деления ещё на 5 — когда по графику снимают значение между
  подписями или строят по точкам (то же поле у вопроса `plot`).
- `graph.chart_type` — `"line"` (по умолчанию) / `"bar"` / `"scatter"`, см.
  `charts-and-graphs.md`. Неизвестное значение — ошибка валидации; для
  `"bar"` допустима только одна серия (столбики нескольких серий рисовались
  бы друг поверх друга), и `y_range` обязан начинаться с 0 (столбик от
  ненулевого основания врёт о соотношении высот).
- `list.marker` — `"none"` / `"number"` / `"letter"` — визуальный префикс
  пункта; `columns` — `"single"` / `"two"` / `"inline"` — раскладка.
  Одноколоночные списки чередуют фон строк (зебра).
- `instrument` — измерительный прибор со шкалой (задачи на цену деления,
  показания, погрешности). `kind` — закрытый словарь из 15 видов: `ruler`,
  `cylinder`, `thermometer`, `dynamometer`, `ammeter`, `voltmeter`,
  `manometer`, `scale_dial`, `speedometer`, `stopwatch`, `caliper`,
  `balance`, `multimeter`, `digital_scale`, `digital_stopwatch`;
  `min`/`max` — пределы шкалы,
  `step` — цена деления (обязана делить диапазон нацело; число делений
  ограничено читаемостью; у цифровых приборов `step` — дискретность табло,
  показание обязано быть ей кратно), `label_step` — опциональный шаг
  подписей штрихов в единицах величины (кратен `step`; только приборы со
  штрихами; число подписей ограничено читаемостью — превышение лимита
  это ошибка, а не молчаливое прореживание): без него подписи
  прореживаются автоматически до круглого шага, с ним ряд подписей
  зафиксирован автором, `value` — опциональное показание (у
  линейки — правый край измеряемого бруска; у аналоговых шкал может лежать
  **между** штрихами — это валидно и даёт задачи на погрешность отсчёта),
  `caption` — подпись под прибором. Метрология: `accuracy_class` — класс
  точности на шкале (только стрелочные, закрытый ряд ГОСТ), `ranges` — два
  предела двухпредельного прибора с двойной шкалой (только
  `ammeter`/`voltmeter`; `min` ≤ 0 — отрицательный `min` даёт заход шкалы
  в минус, `max` = больший предел, внутренняя шкала обязана быть круглой),
  `vernier` — число делений нониуса штангенциркуля
  (только `caliper`; 10 или 20, `value` кратен точности
  нониуса), `weights` — гири рычажных весов (только `balance`: `value` —
  масса тела слева, гири справа с повторами, `step` — наименьшая гиря
  набора; весы рисуются всегда в равновесии, чашки комбинируются свободно
  под тип задачи). Показание-ответ живёт не здесь, а в вопросе рядом
  (`instrument` — чистый компонент). Подробности и типичные шкалы —
  `references/artifacts/instruments.md`.

- `paper` — размеченное место для работы ученика: линии под решение,
  клетка, миллиметровка, точки, чистое поле. Компонент, а не поле вопроса:
  место под ответ — это раскладка, а её в payload вопроса не бывает
  (принцип 2 в `docs/schema-design-principles.md`); ставится **соседним
  блоком** внутри того же `task`/`part`, обычно сразу за вопросом.
  `ruling` — закрытый словарь: `"lines"` (линии, по умолчанию), `"grid"`
  (клетка), `"mm"` (миллиметровка), `"dots"` (точки), `"plain"` (чистое
  поле в рамке). `rows`/`cols` — высота и ширина **в клетках/строках самой
  разлиновки** (у `mm` клетка — сантиметровая, а не миллиметровая: поле
  «12x12 см» — это `rows: 12, cols: 12`). `cols` обязателен у `grid`/`mm`/
  `dots` (квадратную клетку нельзя растянуть по ширине колонки) и
  необязателен у `lines`/`plain` — без него поле занимает всю ширину
  колонки. Поле шире колонки или неправдоподобно высокое — ошибка
  валидации. Подробности и выбор разлиновки — `references/artifacts/
  paper.md`.
- `answer_line` — строка «Ответ: ______» для короткого ответа (число с
  единицей, одно слово). Полей нет. Отдельный компонент, а не разлиновка
  `paper`: это не площадь, а строчка в текстовом потоке.

**Правило экранирования.** Модель хранит **сырой** авторский текст —
экранирует функция рендера в точке интерполяции, вызывая `esc()`
(`worksheet_builder/render_helpers.py`); `esc()` пропускает буквальные
`<sup>`/`<sub>`. Хелперы `list_html`/`table_html` (components.py) принимают
уже готовую HTML-безопасную разметку — в них сырой текст не передаётся.
Забытый `esc()` в новом виде блока ловится фузз-тестом
(`tests/test_escaping.py`), а не глазами на готовом документе.

## Рендер-хелперы (не компоненты)

Чистые функции «места под ответ» (`worksheet_builder/render_helpers.py`),
которыми функции вопросов пользуются напрямую:

- `blank(width_px=150)` — короткая подчёркнутая линия для ответа в строку.
- `blank_cell()` — пустая ячейка-заглушка для таблицы.
- `bank_list(items)` — «Слова для выбора: …» списком.

## Вопросы

Общий конверт — одинаковый у всех девяти видов:

```json
{ "type": "<вид>", "id": "…", ...поля вида..., "explanation": "…" }
```

- Вопрос живёт только внутри `task` (напрямую или через `part`/`row`).
- `explanation` (опционально, у любого вида) — пояснение к ответу,
  печатается в секции «Ответы» курсивной строкой «Пояснение: …» после
  ответа вида. У `open` требует заполненного `answer` (иначе пояснение
  комментирует отсутствующий ответ); у остальных видов ответ инлайн в
  содержимом и есть всегда.
- У вопроса **нет** `label` и `points` — нумерация и баллы живут на
  контейнерах (`task`, `part`).
- Payload каждого вида — естественные для него поля; правильный ответ
  записан **инлайн**, внутри того элемента содержимого, к которому
  относится (см. принципы). Тело вопроса ответа не показывает — ответ
  уходит в секцию «Ответы».

Контракт рендера (`worksheet_builder/questions.py`): у каждого вида пара
функций — `render_<вид>(model)` (тело: бланки, варианты, оси) и
`answer_<вид>(model)` (компактный ответ для секции «Ответы»; пустая строка
— ответа нет). Общий конверт (`explanation`) печатает сборщик секции
(`build_answers_section` в `document.py`). Валидация payload —
pydantic-модель вида в `worksheet_builder/models.py` (выполняется при
загрузке файла, с сообщением, какой инвариант нарушен и в каком блоке);
функции рендера получают уже валидную модель и только рендерят.

### `open` — открытый вопрос

```json
{ "type": "open", "answer": "s = υt = 5·10 = 50 м" }
```

- `answer` (опционально) — решение/ответ; печатается в секции «Ответы».
  Без него `explanation` задавать нельзя.
- **В теле документа не печатает ничего.** Условие — соседний `text`-блок
  (обязателен, см. «Инвариант условия»), место под ответ — соседний
  компонент: `paper` (разлинованное поле) или `answer_line` (строка
  «Ответ: ___»). Места под ответ может не быть, если отвечают устно или
  ответ пишут в соседней таблице.

### `choice` — выбор одного/нескольких

```json
{ "type": "choice", "select": "single",
  "options": [
    { "text": "Увеличивается пропорционально времени" },
    { "text": "Не изменяется", "correct": true },
    { "text": "Изменяется случайным образом" }
  ] }
```

- `select`: `"single"` | `"multiple"`.
- `correct: true` — инлайн-пометка правильного варианта; в теле невидима,
  в секции «Ответы» печатается буквой варианта (`б` или `а, в`).
- Рендер: `list_html(marker="letter")`. При `"multiple"` рендерер сам
  печатает строку-подсказку «Отметьте все подходящие варианты.» над списком
  — иначе single и multiple для решающего неотличимы; дублировать её в
  `text`-блоке не нужно.
- Валидация: `single` → ровно один `correct`; `multiple` → хотя бы один.

### `match` — сопоставление

```json
{ "type": "match",
  "left": [
    { "text": "Скорость",  "match": "ms" },
    { "text": "Ускорение", "match": "ms2" },
    { "text": "Путь",      "match": "m" }
  ],
  "right": [
    { "id": "m",   "text": "м" },
    { "id": "ms",  "text": "м/с" },
    { "id": "ms2", "text": "м/с²" }
  ] }
```

- `right` — пул вариантов с явными `id`; может быть длиннее `left`
  (дистракторы — элементы, на которые никто не ссылается).
- `left[].match` — `id` правого элемента. Связь по `id`, поэтому
  перестановка любого списка ничего не ломает.
- Рендер: два списка `list_html` рядом (`marker="number"` слева,
  `marker="letter"` справа); печатная буква правого пункта — позиционная.
  Ответ в секции «Ответы» — сводка «1-б, 2-в…», буквы в сводке совпадают с
  реально напечатанными.
- Валидация: `id` в `right` уникальны; каждый `match` существует в `right`.

### `fill_text` — пропуски в тексте

```json
{ "type": "fill_text",
  "template": "Единица измерения силы в СИ — ___1___.",
  "blanks": { "1": "ньютон" },
  "bank": ["ньютон", "джоуль", "ватт"] }
```

- Плейсхолдер — `___имя___`; `blanks` — имя → значение. Именованная ссылка
  здесь уместна: плейсхолдер — это и есть явный стабильный идентификатор.
- `bank` (опционально) → `bank_list()` перед текстом.
- Рендер: пропуск → `<span class="fill-blank">`; значения пропусков (в
  порядке появления в шаблоне, через `;`) — в секции «Ответы».
- Валидация: в `template` хотя бы один плейсхолдер (без пропусков это
  просто `text`, а не вопрос), и их множество совпадает с ключами `blanks`.
- **Не ставь плейсхолдер внутрь `$...$`/`$$...$$`**: пропуск `___имя___`
  внутри LaTeX-выражения ломает KaTeX-рендер формулы (см. также
  `symbols.md`). Формулируй шаблон так, чтобы пропуск стоял в обычном
  тексте.

### `fill_table` — пропуски в таблице

```json
{ "type": "fill_table",
  "headers": ["t, с", "υ, м/с", "s, м"],
  "rows": [
    ["0", "0", "0"],
    ["1", { "answer": "2" }, "1"]
  ] }
```

- Ячейка — либо готовая строка, либо объект `{ "answer": "…" }` — пропуск с
  ответом инлайн. В теле такая ячейка → `blank_cell()`; значения пропусков
  (в порядке чтения таблицы, через `;`) — в секции «Ответы»; форма
  `headers`/`rows` совпадает с компонентом `table`, которому всё и
  передаётся.
- `bank` (опционально) — как в `fill_text`.

### `plot` — построить график

```json
{ "type": "plot",
  "x_label": "V, м³", "y_label": "p, кПа", "x_range": [0, 5], "y_range": [0, 250],
  "given": null,
  "answer": [{ "label": "1→2", "points": [[1, 6], [2, 3]], "style": "solid" }] }
```

- Оси (`x_label`/`y_label`/`x_range`/`y_range`) и опциональный `chart_type`
  — та же форма полей, что у компонента `graph` (для `"bar"` — не более
  одной серии и в `given`, и в `answer`, и `y_range` с нуля — как у `graph`).
- `given` (опционально) — серии, уже данные решающему на осях; `answer` —
  серии правильного ответа.
- Рендер: тело — `build_chart_svg(series=given или [])`; в секции «Ответы»
  — мини-график `build_chart_svg(series=answer)` — два независимых вызова
  того же генератора, что у компонента `graph`.

### `true_false` — верно/неверно

```json
{ "type": "true_false",
  "statements": [
    { "text": "Скорость — вектор.", "answer": true },
    { "text": "F = ma всегда.",     "answer": false }
  ] }
```

- Рендер: `list_html(marker="none")`, пункт — строка «утверждение +
  пустые квадратики Верно/Неверно»; ответ в секции «Ответы» — по номерам:
  «1 — Верно, 2 — Неверно».

### `rank` — упорядочивание

```json
{ "type": "rank",
  "items": [
    { "text": "Автомобиль: 60 км/ч", "position": 2 },
    { "text": "Пешеход: 5 км/ч",     "position": 1 },
    { "text": "Поезд: 120 км/ч",     "position": 3 }
  ] }
```

- Порядок массива = порядок показа (перемешанный); `position` — правильная
  позиция `1..N` инлайн у каждого пункта.
- Рендер: `list_html(marker="none")`, пункт — «объект + пустой квадратик под
  номер»; ответ в секции «Ответы» — номера пунктов в правильном порядке
  («2, 1, 3»).
- Валидация: `position` — перестановка `1..N` без пропусков/повторов.

### `classify` — классификация

```json
{ "type": "classify",
  "categories": ["Твёрдое", "Жидкое", "Газообразное"],
  "items": [
    { "text": "Железо",   "category": "Твёрдое" },
    { "text": "Вода",     "category": "Жидкое" },
    { "text": "Кислород", "category": "Газообразное" }
  ] }
```

- `category` — инлайн у каждого объекта, значение из `categories`. Категория
  без объектов допустима (категория-дистрактор).
- Рендер: тело — список объектов с `blank()` под категорию у каждого;
  ответ в секции «Ответы» — сводка по категориям («Твёрдое: Железо; …»,
  пустая категория — прочерк).
- Валидация: каждый `category` присутствует в `categories`.

## Реестр блоков

```python
# components.py                      # questions.py — пары тело/ответ
COMPONENT_RENDERERS = {              QUESTION_BODY_RENDERERS = {
    TextModel:       render_text,        OpenModel:      render_open, …}
    TableModel:      render_table,   QUESTION_ANSWER_RENDERERS = {
    GraphModel:      render_graph,       OpenModel:      answer_open, …}
    ListModel:       render_list,
    InstrumentModel: render_instrument,
    PaperModel:      render_paper,
    AnswerLineModel: render_answer_line,
}
# + контейнеры TaskModel, PartModel, RowModel, DocRowModel и HeadingModel
#   (рендерятся в document.py)
```

Один плоский `type`-дискриминатор, имена не пересекаются. Новый компонент
или вид вопроса = pydantic-модель в `models.py` (валидация + данные) +
функции рендера + строки в реестрах и в union (`AnyBlockModel` — внутри
задания, `DocBlockModel` — верхний уровень).

## Примеры (полные)

Простое задание — условие + один вопрос, без букв:

```json
{
  "type": "task",
  "id": "task-01",
  "points": 2,
  "blocks": [
    { "type": "text", "body": "Автомобиль движется равномерно со скоростью υ = 72 км/ч. Какой путь он пройдёт за t = 15 мин?" },
    { "type": "open", "answer": "υ = 20 м/с, t = 900 с, s = υt = 18000 м = 18 км" },
    { "type": "paper", "ruling": "lines", "rows": 4 }
  ]
}
```

Составное задание — общий контекст (текст + график) на уровне задания, два
подзадания-`part`, каждое со своим условием; буквы `а)`/`б)` и баллы — на
`part`:

```json
{
  "type": "task",
  "id": "task-10",
  "points": 5,
  "blocks": [
    { "type": "text", "body": "Велосипедист разгоняется равноускоренно из состояния покоя. На графике показана зависимость его скорости от времени." },
    { "type": "graph", "x_label": "t, с", "y_label": "υ, м/с", "x_range": [0, 5], "y_range": [0, 10],
      "series": [{ "label": "Велосипедист", "points": [[0, 0], [4, 8]], "style": "solid" }] },
    { "type": "part", "points": 2, "blocks": [
      { "type": "text", "body": "Найдите ускорение велосипедиста." },
      { "type": "open", "answer": "a = Δυ/Δt = 8/4 = 2 м/с²" },
      { "type": "paper", "ruling": "lines", "rows": 3 }
    ] },
    { "type": "part", "points": 3, "blocks": [
      { "type": "text", "body": "Используя график, определите путь, пройденный велосипедистом за первые 4 с." },
      { "type": "open", "answer": "s = υt/2 = 8·4/2 = 16 м" },
      { "type": "answer_line" }
    ] }
  ]
}
```

Два подзадания рядом — общий контекст сверху, затем `row` из двух `part`
(колонки поровну); буквы `а)`/`б)` раздаются по сплющенному обходу, как
будто `row` нет:

```json
{
  "type": "task",
  "id": "task-13",
  "blocks": [
    { "type": "text", "body": "Идеальный газ переходит из состояния 1 в 2, затем в 3 (график V-T). Постройте графики процесса в координатах p-V и p-T." },
    { "type": "graph", "x_label": "T, К", "y_label": "V, м³", "x_range": [250, 650], "y_range": [0, 5],
      "series": [{ "label": "1→2→3", "points": [[300, 2], [300, 4], [600, 4]], "style": "solid" }] },
    { "type": "row", "blocks": [
      { "type": "part", "blocks": [
        { "type": "text", "body": "Постройте график в координатах p-V." },
        { "type": "plot", "x_label": "V, м³", "y_label": "p, кПа", "x_range": [0, 5], "y_range": [0, 250],
          "answer": [{ "label": "1→2→3", "points": [[2, 200], [4, 100], [4, 200]], "style": "solid" }] }
      ] },
      { "type": "part", "blocks": [
        { "type": "text", "body": "Постройте график в координатах p-T." },
        { "type": "plot", "x_label": "T, К", "y_label": "p, кПа", "x_range": [250, 650], "y_range": [0, 250],
          "answer": [{ "label": "1→2→3", "points": [[300, 200], [300, 100], [600, 200]], "style": "solid" }] }
      ] }
    ] }
  ]
}
```

Смешанный документ — теория и задания вперемешку (`order` в
`document.json`); нумеруются только `task`-блоки:

```json
{
  "title": "Равномерное движение: конспект и задачи",
  "header": { "subject": "Физика", "grade": "9" },
  "order": ["theory-heading", "theory-text", "task-01", "graph-demo", "task-02"]
}
```

## Явно вне scope

- Иллюстрации/схемы/фото (компоненты помимо `graph`, `instrument` и
  `paper`) — не
  спроектированы. Виды «дополнить схему»/«подписать части рисунка» пока не
  выразимы (см. индекс `references/artifacts/README.md`). Добавляются
  одним новым компонентом + при необходимости одним новым классом вопроса,
  не трогая остальное.
- Вложенные `part` (нумерация глубже `1. → a)`) и вложенные `row` —
  структурно допустимы, рендером не поддержаны, валидация отклоняет.
