# Схема данных рабочего листа v2 (архитектура, спроектирована с нуля)

**Статус: согласованная архитектура, ещё не реализована.** Заменит
`task-schema.md` и текущий `scripts/` при реализации — до этого момента код
продолжает работать по-старому, ничего из этого файла не подключено.

## Три уровня абстракции

Ядро архитектуры — строгое разделение "что нарисовать" и "что это
педагогически значит":

1. **Данные вопроса (JSON)** — у каждого педагогического вида свой JSON со
   своей структурой, контент и ответ вместе, поля естественные именно для
   этого вида (`options`+`correct` для выбора, `left`+`right`+`pairs` для
   сопоставления и т.д.) — не через общие `table.headers`/`rows` с кучей
   `answer_*`-полей поверх.
2. **Компоненты (`text`/`table`/`graph`/`list`)** — чистое отображение, **не
   знают ничего** про вопрос/ответ/правильность. `TableComponent` рисует
   ровно те `headers`/`rows`, которые ему дали. Никаких `answer`,
   `response_size`, `select_mode` и т.п. на компонентах.
3. **Класс вопроса** (по одному на педагогический вид) — хранит данные
   уровня 1, знает, что в них ответ, а что контент, и **сам** решает, что
   передать компонентам уровня 2 в каждом режиме.

"Место под ответ" (разлинованные строки, короткая черта, пустая ячейка для
заполнения) — **не компонент**, а отдельный набор рендер-хелперов (чистые
функции без данных о вопросе), которыми класс вопроса пользуется напрямую
при сборке HTML.

## Задание — один плоский список, без отдельного "стема"

Ранний вариант этого документа заводил отдельную сущность `Stem` для общего
контекста (`main_question`) и отдельно `sub_questions` — с двумя уровнями
`layout`, спецправилом "стем всегда первый и без буквы" и т.д. Это лишний
структурный уровень: задание должно быть **одним блоком**, а не деревом из
разных типов узлов. Учитель/ученик читает задание целиком и по смыслу
понимает, что тут дано, а что нужно решить — схема не обязана заранее
раскладывать это по разным контейнерам.

```
Task {
  id: string
  points?: number
  layout?: Layout                    // партиционирует items на строки
  settings?: {...}
  items: (Component | Question)[]    // 1+, единый упорядоченный список
}
```

- `items` — плоский, упорядоченный, **разнородный** список: элемент либо
  сырой компонент уровня 2 (`text`/`table`/`graph`/`list` — просто
  показывается, без буквы, без ответа), либо объект-вопрос уровня 3
  (`open`/`choice`/`matching`/... — несёт ответ и, если таких элементов
  больше одного, получает букву).
- Какой это тип — видно по значению `type` (общий реестр компонентов и
  вопросов, без пересечения имён — см. "Реестр элементов" ниже).
- Флага `answerable` не существует — **тип элемента сам решает роль**: если
  это компонент — он просто контент; если это вопрос — он несёт ответ.
- Порядок в `items` — это и есть порядок на странице; контекст (например,
  график) можно поставить перед вопросами, между ними или вообще не
  использовать — никакого требования "весь контекст сначала" больше нет
  (в модели со `Stem` оно было — контекст мог идти только один раз, перед
  всеми вопросами).

### Буквы и баллы

Буквы (`a`, `b`, `c`...) получают только элементы `items`, которые являются
**вопросом** (не компонентом), по порядку следования, и только если таких
вопросов в задании больше одного (или есть явный `label` хотя бы у одного).
Явный `label` побеждает всегда; авто-буквы пропускают уже занятые. Элементы-
компоненты (сырой `text`/`table`/`graph`/`list`) букв никогда не получают —
как и раньше, вычисляется на уровне сборки задания (`document.py`), не
внутри самого объекта.

Баллы — независимо на `Task.points` (общий) и `points` каждого вопроса
(рядом с его буквой), не суммируются автоматически.

## Уровень 2: чистые компоненты

```json
{ "type": "text", "body": "Свободный текст." }
```
```json
{ "type": "table", "headers": ["t, с", "υ, м/с", "s, м"], "rows": [["0", "0", "0"], ["1", "2", "1"]] }
```
```json
{ "type": "graph", "x_label": "t, с", "y_label": "υ, м/с", "x_range": [0, 10], "y_range": [0, 20],
  "series": [{"label": "Тело A", "points": [[0,0],[5,10]], "style": "solid"}] }
```
```json
{ "type": "list", "items": ["Не изменяется", "Увеличивается пропорционально времени"], "marker": "letter", "columns": "single" }
```

- `text.body` — строка (поддерживает `<sup>`/`<sub>`/LaTeX как форматирование
  текста — не педагогическое знание, просто разметка).
- `table.rows` — `list[list[str]]`, всегда готовые строки. `table` — для
  настоящей двумерной сетки с подписанными колонками; если данные
  одномерные (последовательность пунктов) — это `list`, не `table` с пустой
  шапкой.
- `graph.series` — опционально, список серий (без него — пустые подписанные
  оси). Никакого `answer_series` — если классу вопроса нужно показать другую
  кривую в тичер-режиме, он создаёт **второй вызов** `GraphComponent` с
  другими `series`.
- `list.items` — `list[str]`, готовые строки (класс вопроса уже вставил
  туда любые галочки/квадратики через рендер-хелперы). `marker` —
  `"none"`/`"number"`/`"letter"` — чисто визуальный префикс пункта. `columns`
  — `"single"`/`"two"`/`"inline"` — раскладка на странице.

**Почему `list`, а не всегда `table`.** Аудит всех классов вопросов показал:
`choice`/`true_false`/`ranking`/`classify`/`matching` — это не двумерные
сетки с шапкой, а последовательности пунктов с опциональной меткой сбоку
(галочка, квадратик "верно/неверно", номер позиции, категория, буква) — тот
же визуальный язык, что уже устоялся в дизайне листа (зебра-строки, буквенные
варианты, два независимых списка для сопоставления — ни один из них не был
HTML-таблицей). `table` остаётся только для настоящих двумерных данных
(`fill_blank_table` — реальная сетка "t/υ/s" с подписанными колонками).

**Почему `key=value` (словарь) — не 5-й компонент.** Почти в каждом классе
вопроса `answer`/`pairs`/`correct`/`blanks` — это словарь. Но компонент —
это то, что имеет собственный **видимый вид на листе**; словарь такого вида
не имеет — он каждый раз превращается в разное: сводную строку через
`answer_block()` (matching), закрашенный квадратик внутри пункта `list`
(true/false), число внутри пункта `list` (ranking), заполненную ячейку
`table` (fill-blank). Ни один словарь не рисуется "как словарь". Общая у них
только форма *данных* (уровень 1), не форма *отображения* (уровень 2).

Компоненты используются в двух местах: (а) классы вопросов уровня 3 создают
их программно при рендере, (б) элементы `Task.items`, которые сами являются
сырым контентом (не вопросом), хранят их напрямую в JSON.

## Рендер-хелперы (не компоненты)

Чистые функции, ничего не знают о конкретном вопросе:
- `lines(n)` — N разлинованных строк под решение.
- `blank(width_mm=40)` — короткая подчёркнутая линия для ответа в строку.
- `blank_cell()` — пустая ячейка-заглушка для таблицы.
- `answer_block(text)` — тичер-only рамка "Ответ: ..." под условием.
- `bank_list(items)` — "Слова/категории для выбора: ..." списком.

Классы вопросов вызывают их напрямую при сборке своего `render()`, наравне
с вызовами компонентов.

## Уровень 3: классы вопросов

Общий контракт:
```python
class Question(ABC):
    type: ClassVar[str]
    label: str | None
    points: int | None

    @abstractmethod
    def render(self, mode: RenderMode) -> str: ...   # student | teacher

    @classmethod
    @abstractmethod
    def from_dict(cls, data: dict) -> "Question": ...

    @abstractmethod
    def to_dict(self) -> dict: ...
```

По одному конкретному классу на педагогический вид. Каждый ниже — со своей
JSON-формой (контент и ответ вместе) и кратким описанием, как он рендерит
себя через `text`/`table`/`graph`/`list` + рендер-хелперы.

### `OpenQuestion` — открытый вопрос (развёрнутый/короткий), "найти ошибку"
```json
{ "type": "open", "prompt": "Тело движется со скоростью 5 м/с. Найдите путь за 10 с.",
  "response": "lines:4", "answer": "s = υt = 5·10 = 50 м" }
```
`response`: `"lines:N"` | `"blank"` | `"none"`. Рендер: `TextComponent(prompt)`
+ `lines(N)`/`blank()`/ничего, в тичер-режиме `answer_block(answer)`. "Найти и
исправить ошибку" — тот же класс, отличие только в содержимом `prompt`.

### `ChoiceQuestion` — выбор (один/много)
```json
{ "type": "choice", "prompt": "...", "options": ["...", "...", "..."],
  "correct": [2], "select_mode": "single", "explanation": "..." }
```
`select_mode`: `"single"` | `"multiple"` — явное поле. Рендер:
`TextComponent(prompt)` + `ListComponent(items, marker="letter")`, где
каждый пункт — вариант, в тичер-режиме к пунктам из `correct` класс сам
приписывает галочку перед вызовом компонента; `explanation` (опционально) →
`answer_block()` в тичер-режиме.

### `MatchingQuestion` — сопоставить
```json
{ "type": "matching", "prompt": "...",
  "left": ["Сила", "Работа", "Мощность"], "right": ["Вт", "Н", "Дж"],
  "pairs": {"0": 1, "1": 2, "2": 0} }
```
`right` — пул вариантов (может быть длиннее `left` — дистракторы). `pairs` —
индекс в `left` → индекс в `right`. Рендер: `TextComponent(prompt)` + **два**
`ListComponent` рядом — `ListComponent(left, marker="number")` и
`ListComponent(right, marker="letter")` (два независимых пронумерованных
списка, не строки с парами); в тичер-режиме — сводка через `answer_block()`
("1-Б, 2-В, 3-А"), собранная из `pairs`.

### `FillBlankTextQuestion` — заполнить пропуск, носитель текст
```json
{ "type": "fill_blank_text", "template": "Единица измерения силы в СИ — ___1___.",
  "blanks": {"1": "ньютон"}, "bank": ["ньютон", "джоуль", "ватт"] }
```
Рендер: класс сам резолвит `template` (у ученика — пропуски заменяются на
`blank()`, у учителя — на значения из `blanks`) в готовую строку, отдаёт её
одним `TextComponent`. `bank` (опционально) → `bank_list()` перед текстом.

### `FillBlankTableQuestion` — заполнить пропуск, носитель таблица
```json
{ "type": "fill_blank_table", "headers": ["t, с", "υ, м/с", "s, м"],
  "rows": [["0", "0", "0"], ["1", null, "1"]], "answers": {"1,1": "2"},
  "bank": null }
```
`null` в `rows` — позиция пропуска (только на входе — класс сам превращает
её в `blank_cell()` для ученика или в значение из `answers` для учителя
перед вызовом `TableComponent`).

### `GraphQuestion` — построить график
```json
{ "type": "graph_question", "prompt": "Постройте график зависимости давления от объёма.",
  "x_label": "V, м³", "y_label": "p, Па", "x_range": [0, 5], "y_range": [0, 250],
  "given": null, "answer": [{"label": "1→2", "points": [[1,6],[2,3],[3,2]], "style": "solid"}] }
```
`type: "graph_question"` (не `"graph"` — это имя занято чистым компонентом,
см. "Реестр элементов" ниже). `given` (опционально) — что уже дано на осях у
ученика. Рендер: `TextComponent(prompt)` + `GraphComponent(..., series=given
или [])` у ученика, `GraphComponent(..., series=answer)` у учителя — два
независимых вызова компонента.

### `TrueFalseQuestion` — да/нет
```json
{ "type": "true_false", "prompt": "Отметьте, верны ли утверждения.",
  "statements": ["Скорость — вектор.", "F=ma всегда."],
  "correct": {"0": true, "1": false} }
```
Рендер: `TextComponent(prompt)` + `ListComponent(items, marker="none")`, где
каждый пункт — утверждение + квадратики "Верно/Неверно" сбоку (собирается
классом в одну строку пункта до вызова компонента); отметка зависит от
`correct` только в тичер-режиме.

### `RankingQuestion` — упорядочивание
```json
{ "type": "ranking", "prompt": "Расставьте по возрастанию.",
  "items": ["Пешеход: 5 км/ч", "Автомобиль: 60 км/ч", "Поезд: 120 км/ч"],
  "correct_order": {"0": 1, "1": 2, "2": 3} }
```
`items` — в перемешанном порядке показа; `correct_order` — верная позиция
(`1..N`, перестановка без повторов). Рендер: `TextComponent(prompt)` +
`ListComponent(items, marker="none")`, где каждый пункт — объект + квадратик
под номер позиции сбоку; позиция подставляется классом только в тичер-режиме.

### `ClassifyQuestion` — классифицировать
```json
{ "type": "classify",
  "prompt": "Распределите вещества по агрегатным состояниям: вода, кислород, железо.",
  "items": ["Вода", "Кислород", "Железо"],
  "categories": ["Твёрдое", "Жидкое", "Газообразное"],
  "answer": { "Твёрдое": ["Железо"], "Жидкое": ["Вода"], "Газообразное": ["Кислород"] } }
```
`answer` — категория → список объектов (каждый объект встречается ровно в
одном списке — проверяется в `validate()`). Список объектов обычно даётся
компактно (в самом `prompt`, через запятую). Рендер: `TextComponent(prompt)`
+ `ListComponent(items, marker="none")` с местом под категорию (`blank()`) у
каждого пункта — только у ученика; у учителя ответ **не** встраивается в
каждую строку, а показывается одной сводкой через `answer_block()`,
собранной прямо по форме `answer` ("Твёрдое: Железо; Жидкое: Вода;
Газообразное: Кислород") — без инверсии словаря.

## Реестр элементов

```python
COMPONENT_TYPES: dict[str, type[Component]] = {
    "text": TextComponent, "table": TableComponent,
    "graph": GraphComponent, "list": ListComponent,
}

QUESTION_TYPES: dict[str, type[Question]] = {
    "open": OpenQuestion, "choice": ChoiceQuestion, "matching": MatchingQuestion,
    "fill_blank_text": FillBlankTextQuestion, "fill_blank_table": FillBlankTableQuestion,
    "graph_question": GraphQuestion, "true_false": TrueFalseQuestion,
    "ranking": RankingQuestion, "classify": ClassifyQuestion,
}

def item_from_dict(data: dict) -> Component | Question:
    t = data["type"]
    if t in COMPONENT_TYPES:
        return COMPONENT_TYPES[t].from_dict(data)
    if t in QUESTION_TYPES:
        return QUESTION_TYPES[t].from_dict(data)
    raise ValueError(f"Unknown item type {t!r}")
```
Два реестра, без пересечения имён `type` (отсюда `graph_question`, а не
`graph`, для класса вопроса). Добавить новый компонент или новый вид вопроса
позже = один новый класс + строка в соответствующем реестре.

## Layout DSL

```
Layout = Row[]
Row = int N          // N элементов идут в одну строку, поровну делят ширину
    | number[]        // явные проценты, длина = число элементов в строке, сумма = 100
```

`Task.layout` партиционирует `Task.items` — единственный уровень раскладки
теперь (раньше было два: `Stem.layout`/`Task.layout`, со спецправилом про
стем — больше не нужно). У конкретных классов вопросов своего `layout` нет
— внутреннее расположение (текст вопроса над данными) зафиксировано в коде
класса.

**Конвенция для одиночного графика:** если строка `layout` содержит ровно
один элемент, а это `graph`-компонент или `graph_question` — использовать
явный `[50]`, а не голое `1` (растянет на всю ширину). Если график не один в
строке (например, `layout: [..., 2, ...]` кладёт два `graph_question` рядом)
— обычное целое, внешний раздел уже даёт нужную ширину.

## Python-реализация (набросок)

```
scripts/
  components/
    __init__.py    # COMPONENT_TYPES реестр + component_from_dict()
    base.py        # Component (ABC) — только render(), никакого answer/mode
    text.py / table.py / graph.py / list.py
  render_helpers.py # lines()/blank()/blank_cell()/answer_block()/bank_list() — не компоненты
  questions/
    __init__.py    # QUESTION_TYPES реестр + question_from_dict()
    base.py        # Question (ABC), RenderMode
    open.py, choice.py, matching.py, fill_blank.py, graph_question.py,
    true_false.py, ranking.py, classify.py
  task.py          # Task (dataclass), item_from_dict() — объединённый реестр
  layout.py        # парсер/валидатор Layout DSL — теперь только для Task.layout
  document.py       # сборка HTML из списка Task + meta, вычисление букв a/b/c
                    # (только для элементов Task.items, которые Question)
  assets.py / strings.py   # без изменений по духу
```

`Component.render()` **без параметра `mode`** — компонент не знает про режим
ученик/учитель, ему просто дают готовые данные для отрисовки (возможно,
дважды — отдельным вызовом на каждый режим). Все решения "что показать в
этом режиме" принимает конкретный класс `Question`.

Правила валидации (`Question.validate()`, уточняются при реализации):
- `RankingQuestion.correct_order` — перестановка `1..N` без повторов/пропусков.
- `ChoiceQuestion` с `select_mode: "single"` — `correct` содержит ровно один индекс.
- `ClassifyQuestion.answer` — каждый объект из `items` встречается ровно в
  одном списке одной категории (списки образуют разбиение `items`).
- Все индексы в `correct`/`pairs`/`correct_order`/`answers` должны
  существовать в соответствующих списках/таблицах.
- `Task.layout` — сумма элементов по строкам равна длине `Task.items`.

## Явно вне scope

- 4-й+ компонент (иллюстрация/схема/фото/чертёж) — не проектируется сейчас;
  добавляется одним новым классом компонента + одним новым классом вопроса,
  не трогая остальное. Пока не выразимы виды "дополнить схему" и "подписать
  части рисунка".
