# Перенос скилла в Settings → Skills (облачный sandbox)

Рабочий документ по миграции скилла `worksheet-builder` из локальной среды
(Claude Code + `uv`) в среду **Settings → Capabilities → Skills** Claude
Desktop / claude.ai, чтобы им могли пользоваться люди **без Claude Code**.

Это dev-документ. В распространяемый бандл скилла он **не входит** (лежит в
корне репо, рядом с `README.md`/`CLAUDE.md`, а не внутри `worksheet-builder/`).

## Цель

Один и тот же скилл должен работать в двух режимах без форка ядра
(`worksheet_builder/` — общий код):

- **Массовый пользователь** — загружает zip скилла в Settings → Skills и
  просит «сделай рабочий лист…». Не имеет ни Claude Code, ни Python, ни `uv`.
  Это **новая целевая аудитория** и главная причина миграции.
- **Разработчик (я)** — продолжает править скилл в этом репо локально: `uv`,
  `python -m worksheet_builder`, `pytest`, golden-снапшоты, CI. Без изменений.

Архитектурный инвариант проекта переносится дословно и в sandbox остаётся
верным: **Claude не пишет итоговый HTML руками — контент живёт в JSON
(`meta.json` + `tasks/*.json`), детерминированный рендерер собирает HTML.**
Визуальную консистентность гарантирует код, а не память между сообщениями.

## Среда выполнения (sandbox Settings → Skills)

- **Облачный Linux-контейнер code-execution** Anthropic, не машина
  пользователя. Скилл (папка со `SKILL.md` + бандл) монтируется в известный
  путь; Claude исполняет вложенные скрипты через bash/code-execution.
- **Python 3 присутствует**; вызов рендерера — напрямую `python …`, без `uv`
  и без установки пакета (`pip install -e`).
- **Файловая система эфемерна и локальна для сессии.** Внутри одного диалога
  контейнер живёт — многошаговая правка черновика работает. **Между
  сессиями состояние не сохраняется**: чтобы вернуться к листу позже,
  пользователь должен загрузить папку-черновик обратно в диалог.
- **Обмен файлами — через загрузку/скачивание**, а не через папку на диске
  учителя. Итог сессии — HTML(ы) *и* папка-черновик JSON на скачивание.
- **Формулы KaTeX** по-прежнему грузятся с CDN — рендерится в браузере того,
  кто открывает HTML. От среды исполнения скилла не зависит (без изменений).

## Ограничения

1. **Зависимость `pydantic>=2`** (вся валидация, `models.py`, 528 строк:
   15 `model_validator`, 9 `field_validator`, 24 `Literal`) должна быть
   доступна в контейнере. Решение — **устанавливать в рантайме** (см. ниже),
   не вшивать: pip в Linux-контейнере сам подберёт правильное бинарное колесо
   `pydantic_core`, что снимает проблему платформенных wheel'ов.
2. **Требуется сетевой доступ контейнера к PyPI** — load-bearing допущение
   всего подхода с runtime-установкой. **✅ ПРОВЕРЕНО (Шаг 0):** PyPI из
   контейнера доступен, `pip install` работает. Подход с runtime-установкой
   подтверждён; вшивание (vendored wheel) не требуется.
3. **Нет `uv`** — контракт запуска `uv run --project …` в sandbox не работает.
4. **Нет постоянной рабочей папки** — модель «в текущей директории учителя»
   заменяется на «папка в рабочей директории контейнера + скачивание/загрузка».
5. **Прекондишн плана пользователя** — загрузка кастомных скиллов.
   **✅ ПРОВЕРЕНО (Шаг 0):** доступна на всех тарифах, тарифного барьера для
   раздачи нет.

Windows-специфика (ASCII-стрелка `->` в ошибках ради cp1251-консоли,
`esc()` с сохранением `<sup>`/`<sub>`) в Linux/UTF-8 просто не мешает —
трогать не нужно.

## Механизм установки зависимостей (runtime, идемпотентно)

Установка встроена в точку входа `worksheet-builder/scripts/render.py`, а не
оставлена на память Claude в тексте SKILL.md:

- на старте `render.py` пытается `import pydantic`; **только если его нет** —
  `pip install -q "pydantic>=2,<3"`. Идемпотентно: «каждый раз» на деле
  означает «один раз на жизнь контейнера», внутри сессии повторные рендеры
  мгновенные;
- пин диапазона `>=2,<3` — детерминизм (гарантированно v2, защита от
  гипотетического ломающего v3). На HTML-вывод версия не влияет — pydantic
  только валидирует, поэтому golden-тесты в репо стабильны;
- при провале pip (нет сети) — внятная ошибка с отсылкой к ограничению №2,
  без сырого traceback;
- `render.py` добавляет корень скилла в `sys.path` и зовёт
  `worksheet_builder.cli.main()` — argv (`<workspace>`, `--task`, `--mode`)
  проходит насквозь. Это просто ещё одна обёртка над тем же `cli.main()`,
  что и локальный `render-worksheet`/`python -m worksheet_builder`.
