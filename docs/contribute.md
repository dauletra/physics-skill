# Разработчикам

Проект открыт: форкайте, добавляйте свои типы иллюстраций и виды заданий.
Устройство подробно — в [архитектуре](architecture.md), принципы схемы
данных — в [принципах](schema-design-principles.md); ниже только то, что
нужно, чтобы начать.

## Запуск

```bash
git clone <репозиторий> && cd physics-skill
pip install -e ".[dev,docs]"
python -m pytest tests -q          # тесты
python tools/dev.py                # живой просмотр иллюстраций и примера
```

Пакет `physics_svg` зависимостей не имеет и не должен их заводить: скилл
обязан работать офлайн, без pip и без сети. Это проверяется тестом, который
сверяет импорты собранного бандла со списком стандартной библиотеки.

## Слои

```
draw/       холст, геометрия, трансформации, стили. Про физику не знает.
elements/   физический словарь: шкалы, штриховка, уровни жидкости.
schema/     ядро валидации на dataclass + аннотациях, JSON Schema.
visuals/    библиотека иллюстраций: одна папка = один тип.
document/   блоки, виды заданий, нумерация, «Ответы», HTML.
```

Зависимости строго вниз. Иллюстрация рисуется **элементами**, а не строками
SVG: если в новом типе появляется `f'<line x1=...'`, скорее всего нужного
элемента просто ещё нет — заведите его в `elements/`.

## Новый тип иллюстрации

Одна папка:

```
src/physics_svg/visuals/<тип>/
  model.py      dataclass-спека и её инварианты
  render.py     (model, canvas) -> рисует элементами
  specs/*.json  примеры
  doc.md        справочник для модели: поля, правила, JSON
  card.md       карточка для учителя: что это и что сказать Claude
```

Регистрация — в `__init__.py` папки. Больше **нигде** ничего править не
нужно: союз типов для валидации, JSON Schema, галерея на сайте,
golden-тесты, справочник в бандле и библиотека заготовок собираются из
реестра.

`tests/visuals/test_conformance.py` проверит за вас, что тип принёс всё
обещанное, что каждая спека рендерится, укладывается в свою рамку,
детерминирована и экранирует авторский текст.

## Новый вид задания

То же самое в `src/physics_svg/document/questions/`: модуль со спекой и
парой рендеров (тело и компактный ответ), рядом `<тип>.md` и
`<тип>.card.md`.

Пример JSON из справочника **и есть** фикстура тестов — она рендерится,
проверяется на эскейпинг и попадает на сайт. Поэтому пример должен быть
рабочим, а не иллюстративным.

Перед тем как проектировать поля, прочитайте
[принципы схемы](schema-design-principles.md): ответ живёт инлайн рядом со
своим содержимым, раскладка не живёт в вопросе, нумерация и баллы — на
контейнерах.

## Проверки перед коммитом

```bash
python -m pytest tests -q
python -m ruff check . && python -m mypy
python tools/build_skill.py        # бандл собирается, SKILL.md ничего не врёт
python tools/build_site.py && zensical build --strict
```

Если рендер изменился намеренно — пересоздайте эталоны
(`REGEN_GOLDEN=1 python -m pytest tests -q`) и **просмотрите диф глазами**.
Тест ловит изменение, но не отвечает на вопрос, стало ли лучше.

## Публикация

Ничего вручную выкладывать не нужно.

- **Каждый push в `main`** пересобирает сайт и кладёт на него свежий
  архив скилла. Ссылка на странице установки всегда ведёт на последнюю
  сборку.
- **Тег `vX.Y.Z`** выпускает версию: прогоняются проверки, собирается
  бандл, создаётся GitHub Release с архивом и разделом из `CHANGELOG.md`.

Порядок выпуска:

1. Поднять версию в `src/physics_svg/__init__.py` и в `pyproject.toml`, затем
   `uv lock` — иначе `uv lock --check` в CI не сойдётся.
2. Переименовать раздел «Не выпущено» в `CHANGELOG.md` в `## [X.Y.Z] — дата`
   и завести пустой «Не выпущено» сверху.
3. `git tag vX.Y.Z && git push --tags`.
4. Сразу после тега поставить в `main` следующую dev-версию (`0.3.0.dev0`),
   `uv lock`, закоммитить.

Тег, не совпадающий с версией пакета, и отсутствующий раздел в
`CHANGELOG.md` роняют выпуск до публикации — архив, чей `VERSION` врёт,
потом не сопоставить с багом.

Четвёртый шаг не косметический, и проверкой не подстрахован. Каждый push в
`main` кладёт на сайт свежий архив, а `VERSION` внутри берётся из
`__init__.py`. Если там остался номер выпущенной версии, то все
промежуточные сборки представляются выпуском — а именно их и скачивают:
страница установки ведёт на сайт, релизы там вторым вариантом. Сверить
номер с тегом на этом пути нельзя, тега нет; остаётся привычка.

Предвыпуск обозначается по PEP 440 — `0.2.0a1`, `0.2.0rc1`. Такой тег
выкладывается с `--prerelease`, то есть не занимает «Latest release»:
за архивом со страницы установки учитель попадает на стабильную версию.
Пока проект не дошёл до `1.0`, нужды в предвыпусках обычно нет — ноль в
старшем разряде сам означает «может ломаться».

Пишите изменения **для учителя**: что теперь можно попросить и что стало
правильнее, а не какие функции переименованы. Этот же текст читают в
релизе.

И буквально: раздел версии тянется до следующего `##`, поэтому в
`CHANGELOG.md` всё, что относится к файлу целиком — формат, что версия
значит для учителя, откуда начинается история, — живёт в шапке, выше
первого `##`. Приписанное в конец файла попадёт в заметки последнего
выпуска (это проверяет `tests/test_release_notes.py`).

## Язык

Код и комментарии — английский. Сообщения об ошибках, справочники и сайт —
русский: их читают учитель и модель, а не контрибьютор.
