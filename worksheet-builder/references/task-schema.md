# Схема данных рабочего листа (v2)

Три уровня абстракции, строго разделяющие "что нарисовать" от "что это
педагогически значит":

1. **Данные вопроса (JSON)** — у каждого педагогического вида свой JSON со
   своей структурой, контент и ответ вместе, поля естественные именно для
   этого вида (`options`+`correct` для выбора, `left`+`right`+`pairs` для
   сопоставления и т.д.) — не через общие `table.headers`/`rows` с кучей
   `answer_*`-полей поверх.
2. **Компоненты (`text`/`table`/`graph`/`list`)** — чистое отображение, **не
   знают ничего** про вопрос/ответ/правильность. `TableComponent` рисует
   ровно те `headers`/`rows`, которые ему дали. Никаких `answer`,
   `response_size`, `select_mode` и т.п. на компонентах.
3. **Класс вопроса** (по одному на педагогический вид) — хранит данные
   уровня 1, знает, что в них ответ, а что контент, и **сам** решает, что
   передать компонентам уровня 2 в каждом режиме (`student`/`teacher`).

"Место под ответ" (разлинованные строки, короткая черта, пустая ячейка для
заполнения) — **не компонент**, а отдельный набор рендер-хелперов
(`scripts/render_helpers.py`) — чистые функции без данных о вопросе, —
которыми класс вопроса пользуется напрямую при сборке своего `render()`.

## Задание — один плоский список, без отдельного "стема"

```
Task {
  id: string
  points?: number
  layout?: Layout                    // партиционирует items на строки
  settings?: {...}                   // резервное поле, ничем пока не потребляется
  items: (Component | Question)[]    // 1+, единый упорядоченный список
}
```

- `items` — плоский, упорядоченный, **разнородный** список: элемент либо
  сырой компонент уровня 2 (`text`/`table`/`graph`/`list` — просто
  показывается, без буквы, без ответа), либо объект-вопрос уровня 3
  (`open`/`choice`/`matching`/... — несёт ответ и, если таких элементов
  больше одного, получает букву).
- Какой это тип — видно по значению `type` (общий реестр компонентов и
  вопросов, без пересечения имён — см. "Реестр элементов" ниже).
- Флага `answerable` не существует — **тип элемента сам решает роль**: если
  это компонент — он просто контент; если это вопрос — он несёт ответ.
- Порядок в `items` — это и есть порядок на странице; контекст (например,
  график) можно поставить перед вопросами, между ними или вообще не
  использовать.

### Буквы и баллы

Буквы (`a`, `b`, `c`...) получают только элементы `items`, которые являются
**вопросом** (не компонентом), по порядку следования, и только если таких
вопросов в задании больше одного (или есть явный `label` хотя бы у одного).
Явный `label` побеждает всегда; авто-буквы пропускают уже занятые. Элементы-
компоненты (сырой `text`/`table`/`graph`/`list`) букв никогда не получают.

`Question` не хранит никакого текста вообще — только `label`/`points`
(чистая метаданные). Номер задания печатается **всегда** своей отдельной
строкой сверху (`N.` + `Task.points`, если есть) — без исключений, без
мерджа с чем-либо. У каждого вопроса — необязательная маленькая строка
**только** из его буквы и/или его `points` (`a) (2 б.)`), без какого-либо
текста — если ни буквы, ни баллов нет, строки нет вообще. Это вычисляется в
`document.py` (сборка задания), не внутри самого объекта вопроса.

Описательный текст вопроса — если он нужен — обычный `text`-элемент в
`Task.items`, идущий **перед** тем вопросом, который он описывает, — просто
ещё один пункт плоского списка, как `graph`/`table` уже сегодня. Никакой
связи между этим текстом и буквой вопроса на уровне разметки нет — это два
независимых элемента списка, просто стоящие рядом по порядку.

Баллы — независимо на `Task.points` (общий) и `points` каждого вопроса
(рядом с его буквой), не суммируются автоматически.

## Уровень 2: чистые компоненты

```json
{ "type": "text", "body": "Свободный текст." }
```
```json
{ "type": "table", "headers": ["t, с", "υ, м/с", "s, м"], "rows": [["0", "0", "0"], ["1", "2", "1"]] }
```
```json
{ "type": "graph", "x_label": "t, с", "y_label": "υ, м/с", "x_range": [0, 10], "y_range": [0, 20],
  "series": [{"label": "Тело A", "points": [[0,0],[5,10]], "style": "solid"}] }
```
```json
{ "type": "list", "items": ["Не изменяется", "Увеличивается пропорционально времени"], "marker": "letter", "columns": "single" }
```

- `text.body` — строка (поддерживает `<sup>`/`<sub>`/LaTeX как форматирование
  текста — не педагогическое знание, просто разметка).
- `table.rows` — `list[list[str]]`, всегда готовые строки. `table` — для
  настоящей двумерной сетки с подписанными колонками; если данные
  одномерные (последовательность пунктов) — это `list`, не `table` с пустой
  шапкой.
- `graph.series` — опционально, список серий (без него — пустые подписанные
  оси). Никакого `answer_series` — если классу вопроса нужно показать другую
  кривую в тичер-режиме, он создаёт **второй вызов** `GraphComponent` с
  другими `series` (см. `GraphQuestion` ниже).
- `list.items` — `list[str]`, готовые строки (класс вопроса уже вставил туда
  любые галочки/квадратики через свои приватные хелперы). `marker` —
  `"none"`/`"number"`/`"letter"` — визуальный префикс пункта. `columns` —
  `"single"`/`"two"`/`"inline"` — раскладка на странице. Одноколоночные
  списки (`columns: "single"`) чередуют фон строк (зебра) — единое правило
  для всех видов, использующих `list` (choice/true_false/ranking/classify/
  matching), а не только для тех двух, что имели зебру исторически.

**Почему `list`, а не всегда `table`.** `choice`/`true_false`/`ranking`/
`classify`/`matching` — это не двумерные сетки с шапкой, а последовательности
пунктов с опциональной меткой сбоку (галочка, квадратик "верно/неверно",
номер позиции, категория, буква) — тот же визуальный язык (зебра-строки,
буквенные варианты, два независимых списка для сопоставления). `table`
остаётся только для настоящих двумерных данных (`fill_blank_table`).

**Почему `key=value` (словарь) — не 5-й компонент.** Почти в каждом классе
вопроса `answer`/`pairs`/`correct`/`blanks` — это словарь, но у него нет
собственного визуального вида — он каждый раз превращается в разное: сводную
строку через `answer_block()` (matching), закрашенный квадратик внутри пункта
`list` (true/false), число внутри пункта `list` (ranking), заполненную ячейку
`table` (fill-blank).

**Правило экранирования.** Компонент хранит уже HTML-безопасный текст —
экранирование делает тот, кто его создаёт. `from_dict()` компонента (для
сырых JSON-элементов `Task.items`) вызывает `esc()` (`render_helpers.py`) на
авторском тексте; классы вопросов, программно строящие компонент
(`TextComponent(body=...)`, `ListComponent(items=[...])` и т.п.), сами
вызывают `esc()` на пользовательском тексте до передачи — `render()` самого
компонента ничего не эскейпит повторно.

Компоненты используются в двух местах: (а) классы вопросов уровня 3 создают
их программно при рендере, (б) элементы `Task.items`, которые сами являются
сырым контентом (не вопросом), хранят их напрямую в JSON.

## Рендер-хелперы (не компоненты)

Чистые функции (`scripts/render_helpers.py`), ничего не знают о конкретном
вопросе:
- `lines(n)` — N разлинованных строк под решение.
- `blank(width_mm=40)` — короткая подчёркнутая линия для ответа в строку.
- `blank_cell()` — пустая ячейка-заглушка для таблицы (тот же визуальный язык
  "пропуска", что и текстовые пропуски).
- `answer_block(lang, text)` — тичер-only рамка "Ответ: ..." под условием.
- `bank_list(lang, items)` — "Слова/категории для выбора: ..." списком.

Классы вопросов вызывают их напрямую при сборке своего `render()`, наравне с
вызовами компонентов. Мелкая визуальная разметка, специфичная одному виду
вопроса и не переиспользуемая между классами (например, `.tf-square`/
`.rank-square`/`.mc-marker`), строится внутри самого модуля вопроса, а не
здесь.

## Уровень 3: классы вопросов

Общий контракт (`scripts/questions/base.py`):
```python
class Question(ABC):
    type: ClassVar[str]
    label: str | None
    points: int | None

    @abstractmethod
    def render(self, mode: Literal["student", "teacher"], lang: str) -> str: ...

    @classmethod
    @abstractmethod
    def from_dict(cls, data: dict) -> "Question": ...

    def validate(self) -> None: ...
```

`render()` отдаёт **только тело/ответ** — саму строку заголовка (номер/буква
+ `points`, без какого-либо текста) строит `document.py` (см. "Буквы и
баллы" выше), читая `label`/`points` объекта вопроса, а не вызывая
`render()` дважды или требуя от каждого из 9 классов заново собирать одну и
ту же разметку. `lang` нужен классам вопросов для строк интерфейса
(`t(lang, ...)` — "Верно"/"Неверно"/"Ответ:" и т.п.), поэтому сигнатура шире,
чем просто `mode`.

На объекте `Question` **нет** никакого поля для текста вопроса. Описательный
текст (условие задачи, инструкция) — это обычный `text`-элемент в
`Task.items`, стоящий перед вопросом, который он описывает (см. "Буквы и
баллы" выше). `to_dict()` в контракте нет: в
конструкции документа он не участвует (обратной сериализации `Question →
JSON` пайплайн не делает), добавлять его заранее "на будущее" не стали.

`validate()` вызывается сразу после `from_dict()` в `questions.
question_from_dict()` — до этого момента экземпляр может быть в
невалидном состоянии; ошибка валидации всплывает при загрузке файла задания
(`render_worksheet.py`), с понятным сообщением, какой конкретно инвариант
нарушен.

По одному конкретному классу на педагогический вид. Каждый ниже — со своей
JSON-формой (контент и ответ вместе) и кратким описанием, как он рендерит
себя через `text`/`table`/`graph`/`list` + рендер-хелперы.

### `OpenQuestion` — открытый вопрос (развёрнутый/короткий), "найти ошибку"
```json
{ "type": "open", "response": "lines:4", "answer": "s = υt = 5·10 = 50 м" }
```
Условие ("Тело движется со скоростью 5 м/с. Найдите путь за 10 с.") — это
`text`-элемент перед этим вопросом в `items`, не поле на самом вопросе.
`response`: `"lines:N"` | `"blank"` | `"none"`. Рендер: `lines(N)`/
`blank()`/ничего, в тичер-режиме `answer_block(lang, answer)`. "Найти и
исправить ошибку" — тот же класс, отличие только в содержимом
предшествующего текста.

### `ChoiceQuestion` — выбор (один/много)
```json
{ "type": "choice", "options": ["...", "...", "..."],
  "correct": [2], "select_mode": "single", "explanation": "..." }
```
`select_mode`: `"single"` | `"multiple"` — явное поле. Рендер:
`ListComponent(items, marker="letter")`, где каждый пункт — вариант, в
тичер-режиме к пунктам из `correct` класс сам приписывает галочку
(`.mc-marker`) перед вызовом компонента; `explanation` (опционально) →
`answer_block()` в тичер-режиме. Валидация: индексы `correct` в границах
`options`; `select_mode: "single"` → ровно один индекс в `correct`.

### `MatchingQuestion` — сопоставить
```json
{ "type": "matching",
  "left": ["Сила", "Работа", "Мощность"], "right": ["Вт", "Н", "Дж"],
  "pairs": {"0": 1, "1": 2, "2": 0} }
```
`right` — пул вариантов (может быть длиннее `left` — дистракторы). `pairs` —
индекс в `left` → индекс в `right`. Рендер: **два** `ListComponent` рядом —
`ListComponent(left, marker="number")` и `ListComponent(right, marker="letter")`
(два независимых пронумерованных списка, не строки с парами), обёрнутые в
`.matching-columns`; в тичер-режиме — сводка через `answer_block()` ("1-b,
2-c, 3-a"), собранная из `pairs`, буквы в сводке совпадают с теми, что
реально напечатаны у правого списка. Валидация: ключи/значения `pairs` в
границах `left`/`right`.

### `FillBlankTextQuestion` — заполнить пропуск, носитель текст
```json
{ "type": "fill_blank_text", "template": "Единица измерения силы в СИ — ___1___.",
  "blanks": {"1": "ньютон"}, "bank": ["ньютон", "джоуль", "ватт"] }
```
Рендер: класс сам резолвит `template` (у ученика — пропуски заменяются на
`<span class="fill-blank">`, у учителя — на значения из `blanks`) в готовую
строку, отдаёт её через `TextComponent`. `bank` (опционально) →
`bank_list()` перед текстом. Валидация: множество ключей `___key___` в
`template` совпадает с ключами `blanks`.

### `FillBlankTableQuestion` — заполнить пропуск, носитель таблица
```json
{ "type": "fill_blank_table", "headers": ["t, с", "υ, м/с", "s, м"],
  "rows": [["0", "0", "0"], ["1", null, "1"]], "answers": {"1,1": "2"},
  "bank": null }
```
`null` в `rows` — позиция пропуска (только на входе — класс сам превращает
её в `blank_cell()` для ученика или в значение из `answers` для учителя
перед вызовом `TableComponent`). Валидация: каждая `null`-позиция имеет
соответствующий ключ `"r,c"` в `answers`.

### `GraphQuestion` — построить график
```json
{ "type": "graph_question",
  "x_label": "V, м³", "y_label": "p, Па", "x_range": [0, 5], "y_range": [0, 250],
  "given": null, "answer": [{"label": "1→2", "points": [[1,6],[2,3],[3,2]], "style": "solid"}] }
```
`type: "graph_question"` (не `"graph"` — это имя занято чистым компонентом).
`given` (опционально) — что уже дано на осях у ученика. Рендер:
`GraphComponent(..., series=given или [])` у ученика, `GraphComponent(...,
series=answer)` у учителя — два независимых вызова компонента.

### `TrueFalseQuestion` — да/нет
```json
{ "type": "true_false",
  "statements": ["Скорость — вектор.", "F=ma всегда."],
  "correct": {"0": true, "1": false} }
```
Рендер: `ListComponent(items, marker="none")`, где каждый пункт — строка
`.tf-line` (утверждение слева + квадратики "Верно/Неверно" справа,
собранная классом в одну строку до вызова компонента); отметка (`.tf-square`)
зависит от `correct` только в тичер-режиме. Валидация: ключи `correct` в
границах `statements`, значения — `bool`.

### `RankingQuestion` — упорядочивание
```json
{ "type": "ranking",
  "items": ["Пешеход: 5 км/ч", "Автомобиль: 60 км/ч", "Поезд: 120 км/ч"],
  "correct_order": {"0": 1, "1": 2, "2": 3} }
```
`items` — в перемешанном порядке показа; `correct_order` — верная позиция
(`1..N`, перестановка без повторов). Рендер: `ListComponent(items,
marker="none")`, где каждый пункт — `.tf-line` (объект + `.rank-square` под
номер позиции); позиция подставляется классом только в тичер-режиме.
Валидация: `correct_order` — перестановка `1..N` без пропусков/повторов.

### `ClassifyQuestion` — классифицировать
```json
{ "type": "classify",
  "items": ["Вода", "Кислород", "Железо"],
  "categories": ["Твёрдое", "Жидкое", "Газообразное"],
  "answer": { "Твёрдое": ["Железо"], "Жидкое": ["Вода"], "Газообразное": ["Кислород"] } }
```
`answer` — категория → список объектов (каждый объект встречается ровно в
одном списке — проверяется в `validate()`). Рендер: у ученика —
`ListComponent(items, marker="none")` с местом под категорию (`blank()`) у
каждого пункта; у учителя — тот же список без места под ответ (справочно) +
одна сводка через `answer_block()`, собранная прямо по форме `answer`
("Твёрдое: Железо; Жидкое: Вода; Газообразное: Кислород"). Валидация:
объединение всех списков `answer.values()` — точное разбиение `items` (без
пропусков/повторов).

## Реестр элементов

```python
COMPONENT_TYPES: dict[str, type[Component]] = {
    "text": TextComponent, "table": TableComponent,
    "graph": GraphComponent, "list": ListComponent,
}

QUESTION_TYPES: dict[str, type[Question]] = {
    "open": OpenQuestion, "choice": ChoiceQuestion, "matching": MatchingQuestion,
    "fill_blank_text": FillBlankTextQuestion, "fill_blank_table": FillBlankTableQuestion,
    "graph_question": GraphQuestion, "true_false": TrueFalseQuestion,
    "ranking": RankingQuestion, "classify": ClassifyQuestion,
}
```
Два реестра, без пересечения имён `type` (отсюда `graph_question`, а не
`graph`, для класса вопроса). Добавить новый компонент или новый вид вопроса
позже = один новый класс + строка в соответствующем реестре
(`scripts/components/__init__.py` / `scripts/questions/__init__.py`).

## Layout DSL

```
Layout = Row[]
Row = int N          // N элементов идут в одну строку, поровну делят ширину
    | number[]        // явные проценты, длина = число элементов в строке, сумма = 100
```

`Task.layout` партиционирует `Task.items` — единственный уровень раскладки.
У конкретных классов вопросов своего `layout` нет — внутреннее расположение
(например, две колонки `matching`) зафиксировано в коде класса.

**Конвенция для одиночного графика:** если строка `layout` содержит ровно
один элемент, а это `graph`-компонент или `graph_question` — использовать
явный `[50]`, а не голое `1` (растянет на всю ширину). Если график не один в
строке (например, `layout: [..., 2, ...]` кладёт два `graph_question` рядом)
— обычное целое, внешний раздел уже даёт нужную ширину.

## Примеры (полные)

```json
// Простой открытый вопрос — текст-условие + вопрос, без буквы
{
  "id": "task-01",
  "points": 2,
  "items": [
    { "type": "text", "body": "Автомобиль движется равномерно со скоростью υ = 72 км/ч. Какой путь он пройдёт за t = 15 мин?" },
    { "type": "open",
      "response": "lines:4",
      "answer": "υ = 20 м/с, t = 900 с, s = υt = 20 * 900 = 18000 м = 18 км" }
  ]
}
```

## Реализация (структура файлов)

```
scripts/
  components/
    __init__.py    # COMPONENT_TYPES реестр + component_from_dict()
    base.py        # Component (ABC) — только render(), никакого answer/mode
    text.py / table.py / graph.py / list.py
  render_helpers.py # lines()/blank()/blank_cell()/answer_block()/bank_list() — не компоненты
  questions/
    __init__.py    # QUESTION_TYPES реестр + question_from_dict() (вызывает validate())
    base.py        # Question (ABC), RenderMode
    open.py, choice.py, matching.py, fill_blank.py, graph_question.py,
    true_false.py, ranking.py, classify.py
  task.py          # Task (dataclass), item_from_dict() — объединённый реестр
  layout.py        # парсер/валидатор Layout DSL
  document.py      # сборка HTML из списка Task + meta, вычисление букв a/b/c
                    # (только для элементов Task.items, которые Question)
  assets.py / strings.py   # без изменений по духу
```

## Явно вне scope

- 4-й+ компонент (иллюстрация/схема/фото/чертёж) — не спроектирован и не
  реализован. `graph` — единственный визуальный компонент v2; старые
  `svg_snippet`/`raw_svg` не перенесены (см. `scripts/visuals.py` — там
  остался только `build_chart_svg`). Виды "дополнить схему"/"подписать части
  рисунка" пока не выразимы; добавляются одним новым классом компонента +
  одним новым классом вопроса, не трогая остальное.
