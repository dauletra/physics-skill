# Проект: скилл worksheet-builder

Этот репозиторий *и есть* один скилл Claude (`worksheet-builder/`) плюс папка
для черновых выводов (`preview-worksheet/`). Здесь нет приложения для сборки
или тестового набора для запуска — «разработка» здесь означает правку
SKILL.md/references/скрипта скилла и проверку через рендер примерного
workspace.

## Ключевое архитектурное правило

Скилл никогда не пишет итоговый HTML рабочего листа руками. Контент живёт в
маленьких JSON-файлах (`meta.json` + `tasks/task-NN.json`); `scripts/`
детерминированно рендерит их в HTML (`render_worksheet.py` — тонкий CLI, вся
логика — в соседних модулях, см. подробный разбор ниже). Это разделение
существует, чтобы правка одного задания не требовала чтения/переписывания
всего документа. **Не возвращай рукописный HTML-вывод** при правке этого
скилла — если для изменения нужно новое визуальное поведение, меняй
рендерер/CSS, а не HTML конкретного задания.

Поддерживается только русский язык (`meta.json → "language": "ru"`).
Служебные строки интерфейса живут в `STRINGS` (`scripts/strings.py`). Не
добавляй в схему задания языковые поля контента (`body_ru` и т.п.).

Настройка вёрстки/визуала — только через поля JSON (`meta.json.print_margins`,
`response`/`marker`/`columns` на блоках), никогда
через интерактивные элементы в сгенерированном HTML: единственный клиентский
JS — пассивный `paginate()` в `LAYOUT_JS` (экранное превью разбивки на
страницы), никаких тулбаров/hover-контролов, которые бы что-то переключали, в
скилле больше нет и заново их добавлять не стоит без явного запроса — любая
настраиваемая вещь должна быть полем в JSON, а не только кликом в браузере.

**Архитектура задания — дерево блоков (v3)** (полностью реализована, см.
`worksheet-builder/references/task-schema.md`; принципы, по которым
проектируется структура нового вида блока, — в
`worksheet-builder/references/schema-design-principles.md`):
- **Чистые компоненты** (`text`/`table`/`graph`/`list`,
  `scripts/components/`) — только отрисовка, никакого знания об
  ответе/правильности/режиме.
- **Классы вопросов** (`scripts/questions/`, по одному на педагогический
  вид: `open`, `choice`, `match`, `fill_text`, `fill_table`, `plot`,
  `true_false`, `rank`, `classify`) — естественные поля своего вида, ответ
  записан **инлайн** внутри элемента содержимого (`correct: true` на
  варианте, `position` на пункте, `{"answer": …}` вместо ячейки таблицы),
  никаких параллельных индексных структур; класс сам решает, что передать
  компонентам в режиме `student`/`teacher`. Конверт одинаков у всех девяти:
  `type` + опциональные `id`/`explanation`; `label`/`points` на вопросе не
  живут.
- **Контейнер `part`** (подзадание) — компоненты-контекст + ровно один
  вопрос; буква (`a)`/`b)`) и `points` подзадания — на нём, не на вопросе.
- **Layout-контейнер `row`** — дети стоят колонками в одну строку, ширина —
  опциональный инлайн `width` (проценты, все-или-никто, сумма ≤ 100) на
  прямом ребёнке `row`. `row` **прозрачен** для инвариантов состава и букв
  (`iter_flat` в task.py): раскладка меняет только геометрию, никогда —
  смысл/нумерацию. Вложенный `row` запрещён.

`Task { id, points?, blocks: (Component | Question | Part | Row)[] }` —
смысловая связь ("этот текст описывает этот вопрос", "эти блоки рядом")
выражается вложенностью, а не соседством в списке. Инварианты состава
(валидируются при загрузке, с путём до блока в сообщении об ошибке, по
сплющенному обходу): `part` и голый вопрос не бывают соседями; голый вопрос
на уровне задания — не более одного; вложенные `part`/`row` структурно
зарезервированы, но отклоняются валидацией. Одиночный график в `row` не
заворачивается — его ширина всегда ограничена `max-width: 88mm` в CSS,
`row` — только для настоящего "рядом" (см. design-system.md).
Иллюстрации/схемы (`svg_snippet`/`raw_svg` из старой модели) не перенесены и
не спроектированы — намеренно вне scope, см. "Явно вне scope" в
`task-schema.md`; `graph`/`plot` — единственный визуальный элемент.

## Где что лежит

- `worksheet-builder/SKILL.md` — рабочий процесс, которому Claude следует при использовании скилла
- `worksheet-builder/references/task-schema.md` — JSON-схема для meta.json, дерева блоков (`part`, компоненты) и каждого вида вопроса
- `worksheet-builder/references/schema-design-principles.md` — принципы проектирования схемы (связь только вложенностью, метаданные на контейнерах, ответ инлайн, форма payload повторяет форму компонента и т.д.) + чек-лист нового вида вопроса. Новый вид блока проектируй по нему.
- `worksheet-builder/references/design-system.md` — CSS-токены дизайна (шрифты, поля, шапка, нумерация, ширина графика, зебра-полосы `ListComponent`). Держи этот файл в синхроне с `BASE_CSS` (`scripts/assets.py`) при изменении любого из них.
- `worksheet-builder/references/charts-and-graphs.md` — формат данных графика (`x_range`/`y_range`/`series`) и ч/б-безопасный код визуалов
- `worksheet-builder/references/symbols.md` — правило приоритета текст → `<sup>`/`<sub>` → LaTeX для любых не-ASCII обозначений, плюс таблица греческого алфавита и список греческих букв, визуально неотличимых от латинских в шрифтовом стеке дизайн-системы (проверено рендером, а не предположено). Специфичная для проекта конвенция: скорость — это `υ` (ипсилон), а не латинская `v` — `v` в этом шрифте рендерится неотличимо от `ν` (ню, частота). Не "упрощай" пример обратно к латинской `v` для скорости, не перечитав этот файл.
- `worksheet-builder/scripts/` — единственное место, генерирующее HTML, разложенное на несколько модулей и два подпакета вместо одного файла:
  - `render_worksheet.py` — тонкая CLI-точка входа (argparse, `load_workspace()`, `main()`); сам импортирует `build_document` из `document.py` и ничего не знает про схему задания (не трогает `Task`/`Component`/`Question` напрямую).
  - `assets.py` — статические блобы: `KATEX_HEAD`, `_BASE_CSS_TEMPLATE`/`build_base_css()`, `LAYOUT_JS`, плюс Python-словарь `PRINT_MARGIN_PRESETS`. Печатного подвала с номером страницы нет — вместо этого `paginate()` из `LAYOUT_JS` разбивает экранный поток на карточки `.a4-page` (JS-вычисленное приближение печатной пагинации, а не рукописное) и ничего не переключает — чисто пассивный превью. Поля печати (`meta.json.print_margins`) резолвятся в mm один раз при сборке через `build_base_css()`/`resolve_print_margin_mm()` и печекутся прямо в CSS (`--page-margin` и `@page`) — никакого рантайм-тулбара для этого больше нет; см. раздел "Page-view" в `references/design-system.md` о том, как это всё сочетается, включая то, почему пресет полей "Минимум" — задокументированное приближение, а не точное значение Chrome.
  - `strings.py` — `STRINGS`/`t()`, служебные подписи листа.
  - `render_helpers.py` — `esc()`, `LETTERS`/`LOWER_LETTERS` + рендер-хелперы уровня "место под ответ" (`lines()`/`blank()`/`blank_cell()`/`answer_block()`/`bank_list()`), которыми классы вопросов пользуются напрямую. `esc()` намеренно пропускает буквальные теги `<sup>`/`<sub>` (см. `SUPSUB_TAGS`) вместо экранирования всего подряд — именно это позволяет JSON заданий использовать их по `symbols.md`; не заменяй вызовы `esc()` на голый `html.escape()`. Правило экранирования: компонент/вопрос хранит уже HTML-безопасный текст — эскейпит тот, кто его создаёт (`from_dict()` компонента или сам класс вопроса), не `render()`.
  - `visuals.py` — только генератор графиков (`build_chart_svg`). Иллюстрации/схемы (`SVG_SNIPPETS`, `raw_svg`) не перенесены — намеренно вне scope (см. `task-schema.md`), не добавляй их обратно без нового компонента/класса вопроса под них.
  - `components/` — чистые компоненты, пакет: `base.py` (`Component` ABC, только `render()`), `text.py`/`table.py`/`graph.py`/`list.py`, `__init__.py` (`COMPONENT_TYPES`, `component_from_dict()`). Ни один рендерер компонента не знает про ответ/режим ученик-учитель.
  - `questions/` — классы вопросов, пакет: `base.py` (`Question` ABC — `type`/`id`/`explanation` (без текста, буквы и баллов!), конкретный `render(mode, lang)` = абстрактный `render_body()` + единообразный `explanation`-блок в тичер-режиме, `from_dict`/`validate`, хелпер `envelope()`), по одному модулю на педагогический вид (`open.py`, `choice.py`, `match.py`, `fill_text.py`, `fill_table.py`, `plot.py`, `true_false.py`, `rank.py`, `classify.py`), `__init__.py` (`QUESTION_TYPES`, `question_from_dict()` — вызывает `validate()` сразу после `from_dict()`). Описательный текст вопроса — не поле на объекте `Question`, а обычный `text`-блок рядом в дереве (внутри его `part` или на уровне задания).
  - `task.py` — `Task` (dataclass: `id`/`points`/`blocks`), `Part` (dataclass: `blocks`/`label`/`points`/`id`/`width`) и `Row` (dataclass: `blocks`/`id`); парсинг дерева блоков (объединённый реестр `COMPONENT_TYPES`/`QUESTION_TYPES` + типы `part`/`row`, без пересечения имён), `iter_flat()` (сплющенный обход — `row` прозрачен), валидация `width` (только на прямом ребёнке `row`, int 1..100, все-или-никто, сумма ≤ 100) и инварианты состава — ошибки с путём до блока (`task-10 -> blocks[2] (id=...)`, ASCII-стрелка `->` намеренно: `→` роняет печать ошибки в cp1251-консоли Windows).
  - `document.py` — сборка одного задания (`render_task`) и всего документа (`build_document`); здесь и только здесь вычисляются буквы `a)/b)` для блоков-`Part` (`assign_part_labels` по `iter_flat`: явный `label` побеждает, авто-буквы пропускают занятые) и строятся две маленькие строки заголовка: номер задания (всегда своя строка, `render_task_number_line`) и буква/баллы подзадания (`render_label_line`, без текста) — `Question.render()` отдаёт только тело/ответ. `render_row()` считает flex-basis колонок как `calc(N% - доля gap)` — константа `ROW_GAP_MM` обязана совпадать с `gap` у `.task-row` в `BASE_CSS`. `build_document()` конвертирует сырые dict-задания через `Task.from_dict()` и резолвит `print_margins` в CSS через `assets.build_base_css()`.
- `worksheet-builder/examples/kinematics-9th-grade/` — проработанный черновик, покрывающий все 9 видов вопросов и оба чистых визуальных компонента (`text`/`graph`) (14 файлов заданий — task-09 показывает иерархию text/sup-sub/LaTeX символов, task-10 — два подзадания-`part` а)/б) вокруг одного общего `graph`, task-13 — `row` из двух `part` бок о бок со своими `plot`, task-11 — `classify`), используется для ручного тестирования
- `preview-worksheet/` — сгенерированная копия основного (`ru`) примера, лежит в корне проекта исключительно для того, чтобы человек мог открыть отрендеренный HTML. **Не часть скилла.** Можно свободно перезаписывать/перегенерировать; не переноси её обратно в `worksheet-builder/`.

## Как проверять изменения

Автотестов нет. После правки любого файла в `scripts/` или CSS:

```bash
python worksheet-builder/scripts/render_worksheet.py preview-worksheet
```

затем открой `preview-worksheet/output/worksheet-teacher.html` (в нём и
вопросы, и блоки с ответами, так что один файл показывает всё) в Preview-тулзе
и проверь визуально — особенно после правок CSS, поскольку слишком широкий
селектор имеет свойство просачиваться туда, где не должен (например, был баг,
когда `svg { width: 100% }`, ограниченный визуальной колонкой, растягивал ещё
и маленькие иконки в легенде графика — починили, ограничив селектор конкретно
`svg.visual-svg`). После правок именно `LAYOUT_JS` (сейчас — только
`paginate()`) статического скриншота недостаточно — поменяй `print_margins` в
тестовом `meta.json` на другой пресет, пересобери и убедись, что количество/
отступы `.a4-page` обновились соответственно, а DOM не задваивается при
повторном открытии файла.

## Известные компромиссы (не "чини" их без согласования)

- **Сгенерированный рабочий лист исходит из того, что учитель всегда онлайн**
  в момент открытия/печати. Опирайся на онлайн-инструменты/CDN полностью,
  вместо добавления офлайн-фолбэков, вендоринга ассетов или
  feature-detection подключения к сети — это осознанное сужение области
  применения, а не недосмотр, который нужно патчить.
- KaTeX грузится с CDN (jsdelivr), а не встроен локально — это держит
  сгенерированный HTML маленьким, но означает, что для просмотра/печати нужен
  интернет. Это частный случай допущения "всегда онлайн" выше, а не отдельное
  исключение.
- Исключение из вышесказанного: учитель может реально оказаться офлайн в
  момент открытия/печати файла (например, печать в школе при плохом/
  отсутствующем wifi), поэтому проверка `if (window.renderMathInElement)` в
  `KATEX_HEAD` (`scripts/assets.py`) остаётся — это не "офлайн-поддержка"
  (формулы всё равно отрендерятся как сырой `$...$`, если KaTeX не
  подгрузился, никакого фолбэк-рендеринга не добавляется), она просто
  избегает необработанного JS-исключения, если CDN-скрипт так и не пришёл.
  Оставь эту проверку; не делай вызов безусловным.
- Размеры viewBox у SVG графиков подобраны под боковую колонку шириной ~36%
  (см. комментарий в `build_chart_svg`, `scripts/visuals.py`), а не под полную
  ширину страницы — фактическую ширину на листе задаёт `max-width: 88mm` у
  `svg.visual-svg` в `BASE_CSS`; если меняешь эту ширину, константы font-size/
  stroke-width в генераторе, скорее всего, тоже нужно подстроить, а не только
  CSS.
