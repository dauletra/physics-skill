# Выгрузка в Word (.docx)

План второго формата вывода. HTML остаётся как есть и развивается дальше;
Word — **второй бэкенд той же вёрстки**, а не второй рендерер и не
конвертер готового HTML.

Документ — проектный: он описывает целевое устройство, зафиксированные
решения и фазы. Читать вместе с [архитектурой](architecture.md).

Статус: **все пять фаз сделаны** — вёрстка выделена, пакет .docx
собирается, иллюстрации приходят фигурами, формулы — формулами, поверхность
скилла про Word рассказывает. Ниже раздел 1 описывает, как было до Ф1.

## 1. Что было до Ф1

Разметка рождалась в трёх местах, и все три — строковые:

| место | что делает | кто зовёт |
|---|---|---|
| `document/html.py` | фрагменты: `div`, список, таблица, пропуск, банк слов, строка «утверждение + контрол» | компоненты и виды заданий |
| `document/components.py`, `document/questions/<вид>.py` | `body(model) -> str` — готовый HTML вида | `render.py` через реестр |
| `document/render.py` | обход дерева, номера, `part`/`row`, секция «Ответы», страница целиком | CLI |
| `draw/nodes.py` | `Node.svg()` — примитивы рисунка | `Canvas.render()` |

Ключевое наблюдение: **дерево уже было, но немедленно схлопывалось в
строку**. `render_body` возвращал `str`, `Inline`/`Block` носили `.html`,
`Canvas.render()` отдаёт текст SVG. Никакой информации о структуре после
этого не оставалось — а Word'у нужна именно структура.

Второе наблюдение: словарь разметки **уже закрыт и мал**. Всё, что умеет
документ, — это абзац, список с маркером, таблица, пропуск (в строке, в
ячейке, «Ответ: ___»), картинка, квадратик под галочку, банк слов, колонки,
отступ подзадания, номер задания в поле, секция ответов. Двенадцать сущностей.
Это и есть промежуточное представление, которое надо просто выписать явно.

Третье: рисунки строятся узлами (`draw/nodes.py`), а не строками SVG, и
`bbox()` считается независимо от вывода. То есть у иллюстраций **уже есть
формато-независимое представление** — достаточно второго сериализатора.

Что мешало (первые три сняты в Ф1):

- ~~`Inline`/`Block` в `answers.py` носят готовый HTML~~ — теперь вёрстку;
- ~~`esc()` вызывается внутри видов заданий~~ — теперь эскейпит бэкенд;
- ~~`<sup>`/`<sub>` живут в тексте как литеральные теги~~ — теперь их
  разбирает `inline.py`, и в Word они станут `w:vertAlign`;
- `paper` рисует разлиновку SVG-паттернами (`canvas.define`) — единственный
  случай, когда узла нет и есть строка;
- KaTeX-формулы `$…$` — клиентский рендер, в Word клиента нет.

## 2. Целевая картина

```
                    ┌─ emit/html.py   -> сегодняшний HTML, байт в байт
модели -> вёрстка ──┤
 (spec)   (layout)  └─ emit/docx/     -> OOXML-пакет

                    ┌─ Node.svg()      -> сегодняшний SVG
модели -> узлы ─────┤
 (spec)   (draw)    └─ draw/shapes.py  -> DrawingML (нативные фигуры Word)
```

Оба разветвления — одинаковой природы: **одна модель, одно дерево, два
сериализатора**. Это прямое продолжение правила «одна модель данных» и
«иллюстрация рисуется элементами, а не строками».

Что это даёт по существу задачи: учитель получает документ, где текст
редактируется как текст, таблица — как таблица, а график — как **набор
фигур Word**, который можно двигать, растягивать и печатать без потери
качества. Не картинку и не «HTML, открытый вордом».

## 3. Зафиксированные решения

| решение | выбор | почему |
|---|---|---|
| способ | второй бэкенд поверх общей вёрстки | HTML→DOCX-конвертер сделал бы CSS-классы контрактом и нарушил «иллюстрация никогда не извлекается из HTML обратно» |
| зависимости | ноль, как и везде: `zipfile` + `xml` из stdlib | `python-docx` невозможен — бандл обязан работать офлайн без pip |
| HTML | вывод не меняется ни на байт; меняется только код, который его производит | golden-файлы `tests/golden/document/*.html` — гарантия, а не обещание |
| иллюстрации | нативные фигуры DrawingML из тех же узлов | вектор, печатается и правится; растеризатора в stdlib нет, а SVG-blip без растрового фолбэка Word не покажет |
| нумерация заданий | литеральный текст с висячим отступом, а не списки Word | нумерация — наш инвариант (теория между заданиями её не сдвигает); авто-нумерация Word перенумерует при первой правке |
| стили | именованные стили Word — прямой аналог `BASE_CSS` | учитель меняет стиль один раз, документ переливается весь; «никакого рукописного оформления по месту» — то же правило, что и для CSS |
| страница | A4, поля 20/15 мм, фиксированы в `styles.py` | печать в Word инженерится (в отличие от HTML — там решение «не инженерим» остаётся) |
| источник для продолжения сессии | остаётся `document.html` со встроенным черновиком | Word перезаписывает пакет при сохранении; обещать круговорот через .docx нельзя |
| совместимость | Word 2010+ | `mc:AlternateContent` с VML-фолбэком ради Word 2007 удваивает работу над фигурами. Другие редакторы не поддерживаются: адресат — учитель с Word |
| формулы | Ф5, подмножество OMML; до неё — текст как есть | по правилу 5 SKILL.md формулы в основном Unicode + `<sup>`/`<sub>`, LaTeX редок |

## 4. Что меняется в контракте вида задания

Было:

```python
def body(model: ChoiceSpec) -> str:            # HTML
    return list_html([esc(o.text) for o in model.options], marker="letter")
```

Стало:

```python
def body(model: ChoiceSpec) -> Block:          # вёрстка
    items = tuple(parse_inline(o.text) for o in model.options)
    return Bullets(items, marker="letter")
```

То есть: **вид задания перестаёт звать `esc()` и перестаёт знать про
разметку вообще**. Он описывает, что напечатать, а не как. Автор нового вида
по-прежнему пишет один модуль, `register(body=, answer=)` — и получает оба
формата даром. Отдельного docx-кода тип не пишет никогда; это и есть
масштабируемость.

`answers.py` меняется так же: `Inline(html)` → `Inline(runs)`,
`Block(html)` → `Block(layout)`. Секция по-прежнему решает вёрстку сама.

Три инварианта переезжают без изменений: два рендера вместо флага режима,
ответ — форма, а не разметка, `None` — ответа нет.

## 5. Слой вёрстки — `document/layout.py`

Закрытый словарь. Ничего «на будущее»: элемент заводится под первый случай,
которому он нужен, — то же правило, что и в `elements/`.

**Инлайн (внутри строки):**

| элемент | откуда взялся | HTML | Word |
|---|---|---|---|
| `Run(text, script)` | авторский текст, `esc()`, `<sup>`/`<sub>` | текст | `w:r` + `w:vertAlign` |
| `Blank(width_ch)` | подчёркивания в тексте | `.blank` | подчёркнутый прогон пробелов |
| `Gap()` | пропуск `fill_text`/`fill_table` | `.fill-blank` | то же, фикс. ширины |
| `Slot(width_px)` | «Ответ: ___», линия у `classify` | `.answer-line` | табуляция с подчёркнутым лидером |
| `Square()` | квадратик под номер у `rank` | `.rank-square` | символ `☐` |
| `Verdict()` | «☐ Верно ☐ Неверно» у `true_false` | `.tf-box` | два `☐` с подписями |
| `Math(latex)` | `$…$` | текст (KaTeX на клиенте) | Ф5: OMML |

**Блоки:**

| элемент | откуда взялся | HTML | Word |
|---|---|---|---|
| `Para(runs)` | абзац `text` | `<p>` | `w:p` |
| `Phrase(runs)` | ответ рядом со своим номером | инлайн без обёртки | прогоны в чужом абзаце |
| `Line(runs)` | «Ответ: ______» | `<div>` | `w:p` без отбивки |
| `Hint(runs)` | «Отметьте все подходящие» | `.choice-hint` | стиль «Подсказка» |
| `Heading(level, runs)` | `HeadingSpec` | `.doc-heading` | стиль «Заголовок листа/раздела» |
| `Rule()` | `DividerSpec` | `<hr>` | абзац с нижней границей |
| `Bullets(items, marker, columns)` | все списки документа | `.list-component` | абзацы с висячим отступом / таблица для колонок |
| `Statement(runs, control)` | строка `true_false`/`rank`/`classify` | `.tf-line` | таблица 2×1 без границ |
| `Lines(rows)` | ответ по строке на элемент | `.answers-rows` | абзацы подряд |
| `Grid(headers, rows)` | `table`, `fill_table` | `<table>` | `w:tbl` |
| `Bank(label, items)` | банк слов, названия групп | `.bank-list` | стиль «Банк слов» |
| `Picture(model, scope)` | иллюстрация | `<svg>` | `w:drawing` (§7) |
| `Spaced(block)` | блок в потоке колонки | `.task-block` | отбивка абзаца |
| `Stack(blocks)` | подряд, без обёртки | конкатенация | подряд идущие абзацы |
| `Columns(blocks, columns)` | `row` обоих уровней | `.task-row` | таблица без границ, заполнение по столбцам |
| `Facing(blocks)` | два столбца `match` | `.match-columns` | то же, шире промежуток |
| `Numbered(number, blocks)` | номер задания | `.task` | висячий отступ |
| `Lettered(letter, blocks)` | буква подзадания | `.task-part` | отступ слева + висячий |
| `Answers(rows)` | секция «Ответы» | `.answers-section` | раздел с верхней границей |

Правило заполнения колонок сверху вниз живёт в `layout.grid_rows()` как
чистая функция: оба бэкенда раскладывают одинаково, потому что считает одно
и то же место.

**Разбор авторского текста — `document/inline.py`.** Одна функция
`parse_inline(text, blanks=…) -> Text`, которая знает про `<sup>/<sub>`,
про прогоны подчёркиваний и (в Ф5) про `$…$`. Раньше это знание было
размазано между `esc()`, подстановкой в компонентах и `svg_text()`. Собранное
в одном месте, оно делает эскейпинг делом бэкенда — как и должно быть по
правилу «модели хранят сырой авторский текст». Флаг `blanks` — разница между
`text`, где подчёркивания разлиновывают строку, и шаблоном `fill_text`, где
место для записи задаётся именем и подчёркивания литеральны.

## 6. Пакет .docx — `document/emit/docx/`

DOCX — это zip с XML. Пишется stdlib целиком.

```
document/emit/docx/
  package.py   OPC-контейнер: части, _rels, [Content_Types].xml, детерминизм
  wml.py       конструкторы элементов: p(), r(), tbl(), tc(), drawing(), эскейпинг
  styles.py    styles.xml + параметры страницы — аналог assets.py::BASE_CSS
  emit.py      вёрстка -> WML
  shapes.py    Picture -> w:drawing (обёртка над draw/shapes.py)
```

Состав пакета (минимальный, всё остальное Word достраивает сам):

```
[Content_Types].xml
_rels/.rels
docProps/core.xml          фиксированные даты — иначе golden плывёт
word/document.xml
word/styles.xml
word/settings.xml          w:defaultTabStop, w:compat
word/_rels/document.xml.rels
```

`wml.py` — то же, чем `draw/nodes.py` является для SVG: **единственное
место, где пишутся угловые скобки**. Если в `emit.py` появляется `f'<w:p>'`
— значит, нужного конструктора ещё нет.

`styles.py` — платформа для «менять разметку»:

| стиль | что оформляет |
|---|---|
| `Обычный` | базовый шрифт, кегль, интерлиньяж |
| `Заголовок листа`, `Заголовок раздела` | `heading` level 1/2 |
| `Задание` | абзац задания: висячий отступ под номер, отбивка снизу |
| `Подзадание` | отступ слева под букву |
| `Вариант`, `Утверждение` | строки списков |
| `Банк слов`, `Подсказка` | мелкий курсив |
| `Таблица материалов` | сетка, шапка с заливкой, выравнивание |
| `Ответы`, `Пояснение` | секция в конце |

Отображение частных случаев:

| случай | решение | почему так |
|---|---|---|
| пропуск в строке | прогон неразрывных пробелов с `w:u single` | остаётся линией при правке текста вокруг |
| «Ответ: ______» | табуляция с подчёркнутым лидером до правого поля | тянется сама при смене полей |
| квадратик | `☐` (U+2610) шрифтом Segoe UI Symbol | печатается, редактируется, не ломает поток |
| колонки | таблица без границ, `w:tblLayout fixed` | единственный способ «рядом» в Word, который не разъезжается |
| номер задания | текст `3.` + `w:ind hanging` | нумерацию считает рендерер, а не Word |
| ширина таблицы | dxa от ширины текстового поля (170 мм = 9639 twips) | одна константа в `styles.py` |

**Детерминизм** — условие для golden-тестов: фиксированный `date_time` у всех
записей zip, фиксированные `docProps/core.xml`, счётчик `docPr id` от обхода,
никаких rsid. Тот же принцип, что и `num()` в `draw/text.py`.

## 7. Иллюстрации: узлы → DrawingML

Самая ёмкая часть. Реализуется в `draw/shapes.py` — сосед `Node.svg()`,
а не переписывание его. Подробности фазы, включая контракт для будущих
типов, — в [15](#15-3).

**Единицы.** EMU: 1 px (96 dpi) = 9525 EMU. Пользовательская единица рендерится
в `SCREEN_SCALE` px — значит `emu(u) = round(u * SCREEN_SCALE * 9525)`. Та же
калибровка, что на экране, поэтому график в Word и в HTML одного физического
размера. Если рисунок шире текстового поля — вписывается целиком (аналог
`max-width: 100%`), коэффициент один на весь рисунок.

**Отображение узлов:**

| узел | фигура |
|---|---|
| `Line` | `wps:wsp` с `a:custGeom` (moveTo/lnTo) |
| `Polyline` | `a:custGeom`, замкнутый — с `a:close` |
| `Rect`, `Circle`, `Ellipse` | пресеты `rect` / `roundRect` / `ellipse` |
| `Path` | `a:custGeom`: `M/L/A/C/Z` → `moveTo/lnTo/arcTo/cubicBezTo/close` — соответствие один в один с `PathBuilder` |
| `Text` | `wps:wsp` с `wps:txbx`, без заливки и контура; `anchor` → выравнивание, `rotate` → `a:xfrm rot` (1/60000 градуса) |
| `Group` | **разворачивается**: трансформация применяется к геометрии детей численно |
| `Style` | `a:ln` (ширина в EMU, `a:prstDash` из `DASH`), `a:solidFill`, `a:alpha` |

**Почему группы разворачиваются, а не переносятся.** DrawingML знает только
сдвиг, масштаб, поворот и отражение — произвольной матрицы у него нет, а
`Transform` в проекте матричный. Численное применение матрицы к точкам
(`Node.transformed(t)`) снимает вопрос целиком и заодно решает случай
растянутой разлиновки, где масштаб по осям разный. Побочный эффект: `Style.
non_scaling` после разворота не нужен.

**Тайлинг (`paper`).** Единственное место, где узла нет и есть строка:
разлиновка рисуется SVG-паттерном. Решение — поднять паттерн до общего
понятия холста:

```python
canvas.tiling(name, step_x, step_y, tile=(Path(...),))   # плитка узлами
canvas.fill_tiled(region, tiling)                        # залить область
```

Для SVG это регистрирует ровно тот же `<pattern>` и `<rect fill="url(#…)">`,
что и сейчас (плитка сериализуется теми же узлами — вывод обязан совпасть
байт в байт, golden'ы иллюстраций это проверят). Для фигур — разворачивается
в явные линии по области. `paper/render.py` при этом становится
формато-независимым и перестаёт содержать разметку — то есть правило
«рисуется элементами, а не строками SVG» наконец выполняется и здесь.

Риск плотности: миллиметровка на поле в полстраницы — это тысячи линий.
Оценить на реальной спеке; если файл распухает, миллиметровка в Word
деградирует до пятимиллиметровой сетки с явным предупреждением при сборке.
Молчаливой деградации быть не должно.

**Отказ вместо тишины.** Неизвестный узел (в первую очередь `Raw`) —
исключение `Unsupported` с указанием типа иллюстрации, и сборка падает
понятным русским сообщением. Пустая рамка вместо графика в напечатанном
листе — худший из возможных исходов.

## 8. Формулы

Ф5, отдельно от всего остального. Подмножество: дроби, корни, степени,
индексы, греческие буквы, `\cdot`, `\pm`, `\times` → OMML (`m:oMath`).
Всё, что вне подмножества, печатается исходным текстом и попадает в отчёт
сборки: «в блоке task-04 формула $\int…$ вставлена как текст».

До Ф5 — то же самое, только подмножество пустое. Это честнее, чем
недоделанный конвертер, который тихо портит формулу.

## 9. Поверхность скилла

**CLI** (`cli.py`):

```
build <папка> --format html            по умолчанию — как сегодня
build <папка> --format docx
build <папка> --format html,docx
build <папка> --handout --format docx
build <папка> --block task-03 --format docx
```

Результат: `output/document.docx`, `output/document-handout.docx`.

**SKILL.md** — новая строка в таблице команд и один абзац в правилах:
Word нужен, когда учитель будет править руками или печатать; источник для
продолжения сессии — по-прежнему `document.html` со встроенным черновиком.
Модель не должна предлагать «продолжить из docx».

**Бандл** — ничего специального: `document/docx/` уезжает вместе с пакетом,
`test_bundle.py` дополнительно прогоняет `render.py build --format docx`
в чистом окружении (это и есть доказательство «ноль зависимостей»).

**Сайт** — рядом с примером документа выкладывается тот же пример в .docx:
учитель видит, что получит, до установки.

**`tools/docx_dump.py`** — распечатать `word/document.xml` с отступами.
Глазная проверка для контрибьютора, аналог `contact_sheet.py`.

## 10. Проверки

| что | как |
|---|---|
| HTML не изменился | существующие golden'ы `tests/golden/document/*.html` — байт в байт, весь рефакторинг Ф1 идёт под ними |
| SVG не изменился | существующие golden'ы иллюстраций — то же самое для Ф3 |

## 13. Чего не делаем

- **Не парсим свой HTML обратно.** Это сделало бы CSS-классы контрактом
  между слоями и противоречит «иллюстрация никогда не извлекается из HTML
  обратно».
- **Не встраиваем HTML через `w:altChunk`.** Дёшево (Word конвертирует сам),
  но вёрстку выбирает конвертер Word, а SVG не переживёт импорт. Мы теряем
  ровно то, ради чего документ строится рендерером, — единый предсказуемый
  вид.
- **Не тянем `python-docx`.** Ноль зависимостей — не стилевое предпочтение,
  а условие работы скилла офлайн.
- **Не заводим второй набор моделей и второй справочник.** Word ничего не
  добавляет в схему данных: тот же JSON, другой сериализатор.
- **Не делаем docx источником для продолжения сессии.** Word перезаписывает
  пакет; обещание кругового рейса было бы ложным.
- **Не заводим настроек оформления в схеме** (шрифт, поля, кегль). Оформление
  — дело стилей Word: учитель меняет стиль в готовом файле, а не поле в JSON.

## 14. Ф2 в деталях

Фаза делает пакет .docx и переводит в него всю вёрстку, **кроме `Picture`** —
иллюстрации в Ф3. Результат фазы: документ без картинок собирается,
открывается в Word и печатается.

Статус: **сделано**. Что разошлось с планом по ходу — в 14.10.

### 14.1. Главное отличие от HTML: Word плоский

HTML вкладывает: задание содержит подзадание, оно — строку, она — блок.
В Word тело документа — **плоская последовательность** `w:p` и `w:tbl`,
вложенности нет вообще. Значит всё, что в HTML делает вложенность, в Word
становится **свойствами абзаца**: отступ слева вместо `.task-part`, отбивка
снизу вместо `.task-block`, висячий отступ вместо гуттера с номером.

Отсюда устройство обхода: `emit.py` спускается по дереву вёрстки, неся с
собой рамку — что навязали внешние контейнеры, — и отдаёт плоский поток.

```python
@dataclass(frozen=True)
class Frame:
    indent: int = 0        # отступ слева, twips: задание, подзадание, ячейка
    hanging: int = 0       # висячий отступ первого абзаца: под номер, под букву
    style: str = "Normal"  # стиль абзаца
    after: int = 0         # отбивка снизу — ставится последнему абзацу блока

def emit(block: Block, frame: Frame) -> list[Node]   # Node = Para | Table
```

Два следствия, которые надо держать в голове с самого начала:

* **отбивка принадлежит абзацу, а не обёртке.** `Spaced` не может «обернуть»
  ничего — он проставляет `w:spacing w:after` последнему абзацу того, что
  внутри. Поэтому эмиттер сначала строит объекты абзацев и только потом
  сериализует их: постфактум править строку XML нельзя;
* **висячий отступ действует на один абзац.** Номер задания встаёт в первый
  абзац задания, остальные абзацы получают тот же отступ слева без висячего —
  так номер оказывается в поле, а текст выровнен по колонке.

### 14.2. Единицы и геометрия

| величина | единица | перевод |
|---|---|---|
| страница, отступы, ширины таблиц | twip = 1/1440 дюйма | `px * 15` |
| кегль | полупункт | `pt * 2` |
| межстрочный интервал | 1/240 строки | `240 * коэффициент` |
| картинка (Ф3) | EMU = 1/914400 дюйма | `px * 9525` |

**Одно правило перевода: 1 px = 15 twips.** Документ HTML свёрстан в пикселях
при 96 dpi, то есть 1 px = 0,75 pt; вся геометрия листа переносится в Word
умножением на 15, а не подбирается на глаз. Отбивка блока 11 px = 165 twips,
отбивка задания 26 px = 390, отступ подзадания 23 px = 345.

Страница: A4 11906 × 16838 twips, поля 20 мм по бокам (1134) и 15 мм сверху и
снизу (850). Ширина текста — 9639 twips = 170 мм, одна константа `TEXT_WIDTH`
в `styles.py`, от неё считаются все ширины таблиц.

### 14.3. `wml.py` — единственное место с угловыми скобками

Конструкторы: `el(tag, attrs, children)`, `p(...)`, `r(...)`, `tbl/tr/tc(...)`,
`text(...)`. Три вещи, которые он обязан делать сам, иначе Word откажется
открывать файл:

1. **Порядок элементов в `w:pPr` и `w:rPr` фиксирован схемой.** Это
   последовательность, а не набор: `w:pStyle` → `w:numPr` → `w:spacing` →
   `w:ind` → `w:jc`; в прогоне `w:rFonts` → `w:b` → `w:i` → `w:color` →
   `w:sz` → `w:u` → `w:vertAlign`. Именно так: подчёркивание **после** кегля,
   надстрочность — последней. Поэтому свойства собираются из упорядоченного
   списка известных ключей, а не из словаря, который передал вызывающий.
2. **Эскейпинг и чистка.** `&`, `<`, `>` в тексте; управляющих символов XML
   1.0 не допускает вообще — их надо вырезать, иначе файл не откроется. Это
   тот же гейт, что `esc()` в HTML-бэкенде, и фузз эскейпинга должен ходить
   и сюда.
3. **`xml:space="preserve"`** на каждом `w:t` с краевыми пробелами — без него
   Word съест пробел перед пропуском и линия приедет к слову.

### 14.4. Пакет

```
[Content_Types].xml     Default: rels, xml; Override на каждую часть
_rels/.rels             ссылки на document.xml и core.xml
docProps/core.xml       dc:title = title манифеста; фиксированные даты
word/document.xml       тело + w:sectPr последним элементом w:body
word/styles.xml         docDefaults + именованные стили
word/settings.xml       w:defaultTabStop, язык проверки орфографии ru-RU
word/_rels/document.xml.rels
```

`package.py` собирает zip. **Детерминизм**: `ZipInfo` с фиксированным
`date_time`, фиксированный порядок частей, фиксированные даты в `core.xml`,
никаких rsid и никаких случайных id. Два запуска обязаны дать одинаковые
байты — на этом стоит golden-тест.

Заголовок документа уходит в `dc:title` (свойства файла), а не на лист:
название печатает блок `heading` с `level` 1, как и в HTML. Жанр документа
по-прежнему собирается из блоков, рендерер не дорисовывает ничего сам.

### 14.5. Стили

Имя стиля учитель видит в панели Word и меняет им весь документ разом — это и
есть «менять разметку». `styleId` латиницей, `w:name` по-русски.

| styleId | w:name | что оформляет | из чего |
|---|---|---|---|
| `Normal` | Обычный | базовый шрифт, 12 pt, интерлиньяж 1,4 | `body` в CSS |
| `SheetTitle` | Заголовок листа | `Heading(1)`, 16 pt жирный | `.doc-heading.level-1` |
| `SectionTitle` | Заголовок раздела | `Heading(2)`, 13,5 pt жирный | `.doc-heading.level-2` |
| `TaskNumber` | Номер задания | жирный, висячий отступ | `.task-num` |
| `Subtask` | Подзадание | отступ слева 345 | `.task-part` |
| `ListItem` | Пункт списка | висячий отступ под маркер | `.list-row` |
| `Bank` | Банк слов | 11 pt | `.bank-list` |
| `Hint` | Подсказка | 10,5 pt курсив | `.choice-hint` |
| `TableCell` | Ячейка таблицы | 11 pt, по центру | `.table-component td` |
| `AnswersTitle` | Заголовок ответов | 13,5 pt жирный | `.answers-title` |
| `AnswerItem` | Ответ | 11 pt, висячий отступ под номер | `.answers-item` |
| `Explanation` | Пояснение | курсив, серый | `.answers-explanation` |

Шрифт — одна константа. Предлагаю `PT Sans` (первый в стеке HTML, лист
выглядит так же); если шрифта нет, Word подставит замену. Альтернатива —
`Arial`, который есть везде, ценой расхождения с экраном. **Решить в начале
фазы**: от шрифта и кегля зависят все ширины пропусков.

### 14.6. Отображение вёрстки

**Инлайн:**

| элемент | WML | замечание |
|---|---|---|
| `Run(text, "")` | `w:r/w:t` | `xml:space="preserve"` при краевых пробелах |
| `Run(text, "sup"/"sub")` | `+ w:vertAlign` | кегль руками не уменьшать — Word делает сам |
| `Blank(width_ch)` | подчёркнутый прогон из `width_ch` неразрывных пробелов | ширина авторская, как в HTML |
| `Gap()` | то же, фиксированной длины (`GAP_CHARS`) | соответствует `min-width: 68px` |
| `Slot(width_px)` | то же, длина из `width_px` через ширину символа | одна функция `_ruled()` на все три |
| `Square()` | `☐` шрифтом Segoe UI Symbol | печатается и правится |
| `Verdict()` | `☐ Верно` + два неразрывных пробела + `☐ Неверно` | один прогон: в HTML это тоже один виджет |

**Блоки:**

| элемент | WML | замечание |
|---|---|---|
| `Para`, `Phrase`, `Line` | `w:p` со стилем из рамки | различаются только отбивкой |
| `Hint` | `w:p` стилем `Hint` | |
| `Heading(level)` | `w:p` стилем `SheetTitle`/`SectionTitle` | |
| `Rule` | `w:p` с `w:pBdr/w:bottom` | абзац-линия, а не «пустой абзац с подчёркиванием» |
| `Bullets` | по `w:p` на пункт: маркер текстом, таб, висячий отступ | нумерация Word **не** используется |
| `Bullets(columns="two")` | таблица без границ, заполнение по столбцам | порядок из `layout.column_order` |
| `Statement` | `w:p` с правой табуляцией у края текста: текст → таб → контрол | повторяет `justify-content: space-between`, включая перенос длинного текста |
| `Lines` | по `w:p` на строку, без отбивки | |
| `Grid` | `w:tbl`, `w:tblLayout fixed`, равные колонки от `TEXT_WIDTH` | шапка с заливкой `EEEEEE` и `w:tblHeader` — повтор на новой странице, чего в HTML нет |
| `Bank` | `w:p`: жирная подпись + перечисление | |
| `Spaced` | `w:spacing w:after` последнему абзацу вложенного | см. 14.1 |
| `Stack` | конкатенация потоков | |
| `Columns`, `Facing` | таблица без границ, ячейка на колонку | ширины равные, у `Facing` промежуток шире |
| `Numbered` | отступ слева всему заданию, номер в первом абзаце с висячим | если первый блок — картинка или таблица, номер уходит в отдельный абзац над ней |
| `Lettered` | тот же приём с буквой, отступ прибавляется к отступу задания | |
| `Answers` | абзац-линия + заголовок + по абзацу на строку | пояснение — отдельный абзац стилем `Explanation` |
| `Picture` | **`Unsupported`** до Ф3 | понятная русская ошибка с именем блока, а не пустая рамка на листе |

Заполнение колонок сверху вниз нужно обоим бэкендам, но по-разному: CSS
раскладывает сам, а таблице надо выдать ячейки построчно. Значит рядом с
`layout.grid_rows` появляется `layout.column_order(count, columns)` — индексы
по рядам, — и обещание «четвёртый пункт последний в левой колонке» остаётся
одним на два формата.

### 14.7. Порядок работы

Каждый шаг проверяем; первый — самый рискованный, поэтому идёт отдельно.

1. **Скелет пакета**: минимальный .docx с одним абзацем «Проба». Открыть в
   Word. Пока он не открывается, остальное писать бессмысленно.
2. `wml.py` с упорядоченными `pPr`/`rPr` и гейтом эскейпинга.
3. `styles.py`: страница, `docDefaults`, стили. Проверить, что в панели стилей
   Word видны русские имена и что правка `Обычный` меняет весь лист.
4. Инлайн: прогоны, `sup`/`sub`, подчёркнутые пропуски, `☐`.
5. Плоский обход с `Frame`: `Para`, `Phrase`, `Line`, `Hint`, `Heading`,
   `Rule`, `Stack`, `Spaced`.
6. `Bullets` и `Statement` (правая табуляция).
7. `Grid` — с повтором шапки.
8. `Columns` и `Facing` + `layout.column_order`.
9. `Numbered` и `Lettered` — дисциплина отступов.
10. `Answers`.
11. `render.py`: `build_docx(doc, blocks, with_answers=…) -> bytes`; в CLI —
    `--format html|docx` и бинарная запись. Раньше это числилось за Ф4, но без
    файла на диске фазу нечем проверить глазами; за Ф4 остаётся поверхность
    **скилла** (SKILL.md, справочники, бандл, сайт).
12. Тесты, golden, `evals/word.md`.

| что | как |

### 14.9. Риски фазы

| риск | что делаем |
|---|---|
| Word отказывается открывать файл и не говорит почему | шаг 1 отдельно и до всего остального; дальше добавлять по одному элементу, проверяя открытие |
| перепутан порядок в `pPr`/`rPr` | порядок зашит в `wml.py` списком, руками свойства не собираются |
| пустая ячейка таблицы без `w:p` | конструктор `tc()` сам дописывает пустой абзац — это требование схемы, а не косметика |
| ширина пропуска «на глаз» | считается от кегля и ширины символа одной функцией; разъедется — правится в одном месте |
| номер задания уезжает от картинки | известное расхождение с HTML, описано в 14.6; проверяется глазами в Ф3 |
| соблазн начать с картинок | картинки — Ф3; в Ф2 `Picture` обязан падать, а не рисовать заглушку, иначе пустая рамка однажды уедет учителю |

### 14.10. Что разошлось с планом

Четыре вещи, которых план не предвидел, — все мелкие, но их стоит знать
перед Ф3.

**Стили задания и подзадания оказались нужны.** План заводил `Task` и
`Subtask` «на всякий случай»; выяснилось, что без них абзацы задания
остаются `Обычный`, и учитель не может изменить вид всех заданий сразу — то
есть теряется ровно то, ради чего формат заводился. Их назначает `Frame.
style`: контейнер задаёт стиль тем абзацам, которые не выбрали свой
(`ListItem`, `TableCell` остаются при своём).

**Таблица не умеет отбивку.** В Word отбивка — свойство абзаца, а у таблицы
абзаца нет. Поэтому `Tbl` с ненулевым `after` дописывает за собой пустой
абзац. Это же требование схемы в другом месте: тело не может кончаться
таблицей, и ячейка не может — `cell()` дописывает абзац сам.

**Правая табуляция сработала.** «Утверждение слева, контрол справа»
получилось одним абзацем с правой табуляцией у края колонки; таблица 2×1,
которую план держал запасным вариантом, не понадобилась.

**`--format` действительно пришлось делать в Ф2**, как и подозревал план
(14.7, шаг 11): без файла на диске фазу нечем проверить. За Ф4 осталась
поверхность скилла — SKILL.md, справочники, бандл, сайт.

Ещё одно, уже про Ф3: `Picture` падает `Unsupported`, и пример `open` тоже
попадает под это — в нём есть `paper`. То есть после Ф3 обязательно
перепроверить конформанс-тест: он сейчас разрешает «либо печатается, либо
падает», и это послабление надо снять.

## 15. Ф3 в деталях

Фаза переводит иллюстрации в нативные фигуры Word. После неё `Unsupported`
из Ф2 исчезает, и любой документ собирается в оба формата.

Статус: **сделано**. Что разошлось с планом — в 15.12.

### 15.1. Осмотр слоя рисования: фаза меньше, чем казалась

План §7 писался до того, как я пересчитал, что библиотека **на самом деле**
рисует. Перепись узлов по `visuals/` и `elements/`:

| узел | вызовов | нужен в Ф3 |
|---|---|---|
| `Line` | 33 | да |
| `Rect` | 23 | да |
| `Text` | 16 | да |
| `Circle` | 14 | да |
| `Path` (через `PathBuilder` и `arc`) | 7 | да |
| `Polyline` | 2 | да |
| `Ellipse` | 0 | нет |
| `Group` | 0 | нет |
| `Raw` | 0 | нет |

Ни один из четырёх нынешних типов не использует `Group`, `Transform`,
`Ellipse` и `Raw`. `Text.rotate` тоже нигде не выставляется: подпись оси
`υ, м/с` стоит горизонтально у наконечника, а не вдоль оси.

**Но переписи сегодняшних вызовов недостаточно, чтобы решить объём фазы.**
Ф7 — это новые типы: механика, цепи, оптика. Их словарь (`elements/`:
пружина, нить, блок, опора, провод с условными обозначениями, луч с линзой)
— это как раз то, что ставится **по якорю и под углом**: пружина рисуется
горизонтально и поворачивается вдоль нити, обозначение резистора садится на
провод под наклоном. А `Group` документирован ровно как механизм такого
размещения — «дети в своей системе координат, чтобы элементы ставились по
якорю, а не пересчитанными абсолютными координатами».

То есть первый же тип из Ф7 упрётся в `Group`, и упрётся в неожиданном
месте: человек добавляет механику, а его останавливает Word-бэкенд, к
механике отношения не имеющий. Поэтому **разворачивание трансформаций
входит в Ф3**, а не откладывается: это тридцать строк (`transformed()` по
узлам), которые превращают «следующий тип может упереться в стену» в «любой
тип работает».

Правило «элемент заводится под первый случай, которому он нужен» этому не
противоречит: оно про **словарь** — не выдумывать размерную линию, пока её
некому нарисовать. Здесь словарь уже есть и задокументирован; речь о том,
чтобы у существующего узла было два сериализатора, а не полтора.
Опубликованный API с одним рабочим бэкендом — это ловушка, а не экономия.

По той же причине в Ф3 входит `Ellipse` (три строки, пресет `ellipse`).
Не входит только `Raw`: он и есть «произвольная SVG-разметка», у которой
в фигурах эквивалента нет и быть не может — см. 15.2.

### 15.2. Контракт роста: чем платит новый тип иллюстрации

Вопрос, на который фаза обязана ответить: что придётся сделать автору
пятого, десятого, двадцатого типа, чтобы его картинка появилась в Word.
Ответ должен быть «ничего», и он держится на трёх вещах.

**Контракт живёт на уровне узла, а не типа.** Тип рисует узлами и про формат
не знает — ровно так же, как вид задания не знает про HTML. Пока новый тип
складывается из существующих примитивов, он работает в Word в тот же день,
что и в HTML, не написав ни строчки. Это уже так и остаётся так.

**Узел без второго сериализатора невозможно завести незаметно.** Сейчас
ничто этого не ловит: новый `Node` с одним `svg()` спокойно пройдёт тесты и
свалится у учителя. Поэтому в Ф3 появляется тест покрытия — он перечисляет
подклассы `Node` и падает, если для какого-то нет перевода в фигуры. Тот же
приём, что `test_conformance.py` применяет к типам иллюстраций: не «не
забудь», а «не соберётся».

Цена нового узла после этого: три метода в одном месте — `svg()`, `bbox()`
и запись в таблице перевода. Это и есть потолок расходов на рост.

**`Raw` объявляется SVG-only и запрещается в рендерерах типов.** Он несёт
произвольную разметку, у которой в DrawingML эквивалента нет — и он же
единственная дыра, через которую тип может «работать в HTML и не работать в
Word». Сообщение об отказе говорит прямо: нужен новый узел, а не сырая
разметка. Это дословно то же правило, что уже действует для генераторов
(«появился `f'<line x1=...'` — заведи элемент»), продлённое на второй
формат. Сегодня `Raw` не использует никто, так что запрет ничего не ломает.

Чего этот контракт **не** покрывает: возможностей SVG, которых в DrawingML
просто нет, — градиентов, обтравки, фильтров. Для чёрно-белой штриховой
графики они не нужны, и в дорожной карте (механика, цепи, оптика) ни одна
не появляется. Если такой случай возникнет, это решение уровня архитектуры,
а не строчка в бэкенде: либо тип обходится без него, либо мы теряем
обещание «один рисунок — два формата».

Отдельно про «посмотреть глазами»: у SVG для этого есть контрольный лист
(`tools/contact_sheet.py`), у Word — ничего. Поэтому в фазу входит
`--docx` у контрольного листа: один файл со всеми спеками всех типов,
открыл — и видно, как новый тип выглядит на бумаге. Без этого автор типа
проверить себя не может, и никакой контракт не поможет.

### 15.3. Куда попадает картинка

`Picture` становится абзацем с одним прогоном, внутри которого — рисунок:

```
w:p / w:r / w:drawing / wp:inline
  wp:extent cx cy            размер рамки в EMU
  wp:docPr id name           id уникален в документе
  a:graphic / a:graphicData uri=…wordprocessingGroup
    wpg:wgp                  группа: одна фигура на узел холста
      wpg:grpSpPr / a:xfrm   off/ext и chOff/chExt — своя система координат
      wps:wsp …
```

Группа (`wpg`) вместо картинки — это и есть «нативные фигуры»: учитель
может выделить подпись и подвинуть её, растянуть график, стереть лишнюю
линию. Пространства имён `wp`, `a`, `wpg`, `wps` добавляются в
`w:document`; `mc:AlternateContent` с VML-фолбэком не пишем — решение
«Word 2010+» уже зафиксировано в §3.

`wp:docPr id` обязан быть уникальным в документе. Счётчик — в эмиттере,
по порядку обхода: тот же принцип, что у скоупа id в SVG, и та же причина —
детерминизм сборки.

Картинка внутри колонки (`row` с графиком в ячейке) достаётся даром:
`Frame.width`, заведённая в Ф2, уже несёт доступную ширину.

### 15.4. Единицы и размер

| что | как считается |
|---|---|
| рамка | `emu(units) = round(units * SCREEN_SCALE * 9525)` — та же калибровка, что на экране |
| толщина линии | то же преобразование, `a:ln w=` |
| кегль подписи | `units * SCREEN_SCALE * 0.75` пунктов, в `w:sz` — полупункты |

Рисунок шире текстовой колонки вписывается целиком, коэффициент один на всю
картинку — аналог `max-width: 100%`.

**Растянутая разлиновка** (`paper` без `cols`) — единственный случай, где
масштаб по осям разный. В HTML это `preserveAspectRatio="none"`: поле
нарисовано на номинальные `COLUMN_WIDTH = 490` единиц и растягивается
браузером до колонки. В Word растягивать нечему, поэтому геометрия
масштабируется анизотропно (x — до ширины колонки, y — один к одному), а
толщины линий остаются как заданы. Ничего изобретать не нужно: стили этих
разлиновок уже помечены `non_scaling=True` — флаг ровно про это и говорит.
**Бэкенд фигур обязан его читать**, иначе строка поля станет ниткой.

### 15.5. Отображение узлов

| узел | фигура | почему так |
|---|---|---|
| `Line`, `Polyline`, `Path` | `wps:wsp` + `a:custGeom` во всю рамку, координаты абсолютные | у горизонтальной линии нулевая высота bbox, а `a:ext cy="0"` невалиден — фигура во всю рамку снимает вопрос целиком |
| `Rect` | `a:prstGeom prst="rect"` со своим `a:xfrm` | ширина и высота ненулевые по построению |
| `Circle` | `a:prstGeom prst="ellipse"` со своим `a:xfrm` | то же |
| `Text` | текстовый блок (`wps:txbx`) | своя рамка обязательна: текст надо где-то разместить |
| `Ellipse` | `a:prstGeom prst="ellipse"` | три строки; не оставлять существующий узел без перевода |
| `Group` | **разворачивается**: трансформация применяется к геометрии детей численно | DrawingML знает только сдвиг, масштаб, поворот и отражение, а `Transform` матричный. Разворот снимает вопрос целиком и заодно решает анизотропный случай (15.4) |
| `Raw` | `Unsupported` с подсказкой «заведи узел» | произвольная разметка — единственная дыра, через которую тип может работать в HTML и не работать в Word (15.2) |

Команды пути переводятся один в один: `M` → `a:moveTo`, `L` → `a:lnTo`,
`C` → `a:cubicBezTo`, `Z` → `a:close`. Дуги `A` **не** переводятся в
`a:arcTo`: у него другая параметризация (угол начала и развёртка вместо
конечной точки), и пересчёт — лишний источник ошибок. Вместо этого
`PathBuilder` уже хранит сэмплы дуги в `extent_points` с шагом 5°;
достаточно дать ему отдавать их как ломаную. Дуга в библиотеке ровно одна
(угол между векторами), и на бумаге пятиградусная ломаная от дуги
неотличима.

### 15.6. Текст — самая тонкая часть фазы

Три несоответствия между SVG и Word, каждое даёт сдвиг, который видно
глазами:

**Базовая линия против верха блока.** В SVG `y` — базовая линия, в Word
текстовый блок позиционируется по верху. Сдвиг вверх на восходящую часть:
константа `_ASCENT = 0.78` уже лежит в `draw/nodes.py` и используется для
`bbox()` — тот же коэффициент, одно место.

**Выключка против якоря.** `text-anchor` = `start`/`middle`/`end`
превращается в блок известной ширины (`text_width()`, тот же оценщик, что
считает bbox) с `w:jc` left/center/right и смещением рамки на 0, −½, −1
ширины.

**Блок не должен ничего добавлять от себя.** `wps:bodyPr` с нулевыми
отступами (`lIns/tIns/rIns/bIns="0"`), `wrap="none"`, `a:noAutofit`, без
заливки и контура. Иначе Word подставит свои поля в 91440 EMU, и каждая
подпись уедет на 2,5 мм.

`<sup>`/`<sub>` внутри подписи: в SVG это `tspan` со сдвигом базовой линии,
в Word — `w:vertAlign`, тот же механизм, что уже написан в Ф2 для текста
документа. `font_weight="bold"` и `letter_spacing` (клеймо прибора) —
`w:b` и `w:spacing`.

### 15.7. Стили

| поле `Style` | DrawingML |
|---|---|
| `stroke`, `width` | `a:ln w=` + `a:solidFill/a:srgbClr` |
| `fill` | `a:solidFill` или `a:noFill` |
| `dash` | `a:prstDash`: `8,4` → `dash`, `1,3` → `sysDot` |
| `opacity` | `a:alpha` (сейчас не используется) |
| `non_scaling` | толщина не умножается на масштаб — см. 15.4 |
| `cap`, `join` | `a:round` / `a:bevel` в `a:ln` |

Цвета уже шестнадцатеричные (`#000`, `#bbb`), нужно только развернуть
короткую форму в шесть знаков.

### 15.8. Разлиновка: тайлинг

Единственное место во всей библиотеке, где узла нет и есть строка:
`paper` рисует клетку SVG-паттерном через `canvas.define`, а поле — как
`Rect` с `fill="url(#…)"`. Для фигур паттернов не существует.

Решение — поднять паттерн до понятия холста, одно на два бэкенда:

```python
grid = canvas.tiling("grid", step=12, tile=(Path("M12 0 L0 0 0 12", _GRID),))
canvas.add(canvas.fill_tiled(BBox(0, 0, width, height), grid))
```

* для SVG `tiling` регистрирует тот же `<pattern>`, что и сегодня, а его
  содержимое сериализуется из узлов плитки — разметка обязана совпасть
  **байт в байт**, это проверят существующие golden'ы иллюстраций;
* для фигур плитка размножается по области явными линиями.

Вложенный случай (`mm`: крупная клетка залита мелкой) выражается тем, что
`Tiling` приводится к строке как `url(#id)` — то есть сегодняшний
`Style(fill=…)` остаётся как есть, — а бэкенд фигур умеет разворачивать
такую заливку рекурсивно.

**Сколько линий получится.** `mm` требует явных `cols`, поле ограничено
`COLUMN_WIDTH = 490` и `MAX_HEIGHT = 900` единиц, мелкий шаг — 3 единицы.
Верхняя граница: 163 вертикали + 300 горизонталей ≈ 460 фигур на самое
большое поле, порядка 90 КБ XML. Деградация до пятимиллиметровой сетки,
которую план держал про запас, **не нужна** — цифры оказались на порядок
меньше, чем я опасался.

### 15.10. Проверки

| что | как |
|---|---|
| SVG не изменился | существующие golden'ы иллюстраций — байт в байт; особенно после перевода `paper` на тайлинг |
| каждая спека переводится | конформанс от реестра: все `visuals/*/specs/*.json` разворачиваются в фигуры без `Unsupported` |
| каждый вид задания | послабление «либо печатается, либо падает» снято: печатается всё |
| рамка соответствует содержимому | те же инварианты, что проверяет `test_conformance` для viewBox: фигуры не выходят за `wp:extent` |
| размер файла | верхняя граница на самое большое `mm`-поле — тест с числом, чтобы разрастание заметил не учитель |
| детерминизм | две сборки документа с картинкой байт в байт |
| новый узел не пройдёт молча | тест покрытия: подклассы `Node` сверяются с таблицей перевода — как `test_conformance` сверяет типы с их спеками |
| трансформации | отдельный тест: точка под матрицей и bbox группы совпадают с тем, что даёт `Transform.apply` |
| независимая проверка | `python-docx` открывает документ с рисунком |
| глазами | `evals/word.md`: график, прибор, разлиновка, векторы — печать и правка подписи |

### 15.11. Риски

| риск | что делаем |
|---|---|
| Word не открывает документ с фигурами | шаг 1 отдельно: одна линия в группе, и только потом всё остальное |
| подписи разъехались | `_ASCENT` и `text_width()` — те же, что считают bbox; расхождение с SVG видно на контрольном листе |
| `bodyPr` по умолчанию добавляет поля | нулевые отступы и `wrap="none"` зашиты в конструктор текстового блока, а не выставляются по месту |

### 15.12. Что разошлось с планом

**Разворот клетки был квадратичным.** План считал, что миллиметровка даст
несколько сотен линий; первая же сборка дала 2400 фигур на поле 6×4 см — по
одной на клетку, а не по одной на линию. Отсюда правило в `Tiling.expanded`:
**ребро клетки становится одной линией через всё поле**, а всё, что ребром
не является (точка точечной разлиновки), по-прежнему повторяется по клеткам.
Самое большое поле, которое допускает схема, — 554 фигуры и 11 КБ, то есть
ровно тот порядок, на который план и рассчитывал. Проверяется тестом с
числом, а не на глаз.

**Дуги переводятся честными дугами, а не ломаной.** План предлагал
сэмплировать их, чтобы не пересчитывать параметризацию. Но пересчёт всё
равно понадобился — для `transformed()`, где повёрнутая дуга перестаёт быть
круговой, — а раз он есть, `a:arcTo` выходит дешевле ломаной и печатается
лучше. Ломаная осталась там, где она неизбежна: под поворотом.

**Оценка ширины подписи оказалась неважной.** План называл это тонким
местом: `text_width()` — оценка, и ошибка в ней сдвинула бы подпись. На
деле блок привязывается тем же краем, каким привязана подпись, и текст
выключается к тому же краю, так что ошибка оценки двигает только невидимый
дальний край блока. Место оказалось прочным.

**`Transform.scale` уже было занято.** Свойство «во сколько раз растянуто»
пришлось назвать `scale_factor`: `Transform.scale` — это конструктор.
Мелочь, но она сломала бы все существующие вызовы молча.

## 17. Ф5 в деталях

Фаза переводит формулы. После неё `$…$` перестаёт быть строкой с долларами:
в Word это объект-формула, который правится редактором формул Word, а в HTML
— ровно то же, что и раньше.

Статус: **сделано**. Что разошлось с планом — в 17.12.

### 17.1. Что происходит сегодня

`Math` из §5 так и не заведён: доллары никто не распознаёт, формула едет
обычным `Run`. В HTML это работает случайно и хорошо — KaTeX ищет доллары в
готовой странице сам. В Word это работает случайно и плохо. Проработанный
пример, который лежит на сайте, прямо сейчас печатает в Word вот это:

```
Кинетическая энергия вычисляется по формуле $$E_k = \frac{m\upsilon^2}{2}$$.
```

То есть в единственном месте примера, где есть LaTeX, Word-файл выглядит
сломанным. Это и есть цена фазы, выраженная одной строкой.

Важно, что случай **редкий по построению**: `references/symbols.md`
запрещает открывать `$…$` ради одной греческой буквы или знака сравнения и
оставляет LaTeX дробям, корням и системам. В примере из шестнадцати заданий
формула ровно одна. Поэтому фаза маленькая, а не «поддержать LaTeX».

### 17.2. Что фаза делает и чего не делает

**Делает:** распознаёт формулу в авторском тексте, заводит `layout.Math`,
переводит закрытое подмножество LaTeX в OMML (`m:oMath`), а всё, что вне
подмножества, печатает исходным текстом и **называет вслух** при сборке.

**Не делает:** формул в иллюстрациях (подписи осей — Unicode и `<sup>`,
LaTeX там не поддерживается и не будет: подпись — часть рисунка, а не
текста), картинки формулы вместо формулы (растеризатора в stdlib нет),
изменений в HTML (KaTeX остаётся клиентским, решение из §3 в силе).

### 17.3. Зафиксированные решения

| решение | выбор | почему |
|---|---|---|
| что переводим | закрытое подмножество, перечисленное в коде таблицей | «поддержать LaTeX» — задача без конца; список растёт по реальной просьбе учителя, а не впрок |
| что вне подмножества | исходный текст **плюс** запись в отчёте сборки | недоделанный конвертер, тихо портящий формулу, хуже честного текста; молчаливой деградации быть не должно — то же правило, что у `Raw` в §15.2 |
| HTML | не меняется ни на байт: `Math` печатается теми же долларами и тем же эскейпингом | golden-файлы `example.html` и `mixed.html` не перегенерировать; расхождение — баг фазы |
| `$$…$$` | входит в фазу: `m:oMathPara`, формула отдельной строкой | конфиг KaTeX уже объявляет этот разделитель, и модель им уже пользуется (`task-10` примера) — оставить его текстом значило бы сломать самый заметный случай |
| одиночный `$` | остаётся текстом | ровно то, что делает KaTeX: пара долларов на одной строке — формула, непарный доллар — доллар |
| шрифт формулы | `Cambria Math` | другого математического шрифта Word не знает; при его отсутствии Word подставляет сам, и это видно глазами, а не молча |
| где живёт код | `document/emit/docx/omml.py` | `wml.py` — единственное место, где пишутся `w:`; `omml.py` — единственное, где пишутся `m:` |
| дерево формулы | парсер отдельно от сериализатора | разбор LaTeX — это разбор, а не печать; на дереве проверяется подмножество и пишутся тесты, не заглядывая в XML |

Два вопроса, которые фаза открывала, решены так:

1. **Отчёт возвращается парой.** `build_docx` отдаёт `Docx(data, notes)`, и
   шесть мест вызова поправлены. Необязательный out-параметр был бы ровно тем
   способом, которым заводится тишина. Печатает записи только CLI;
   `contact_sheet.py` и `build_site.py` игнорируют их осознанно.
2. **Пропуск внутри формулы — ошибка сборки.** `___имя___` внутри `$…$`
   ломает формулу, и раз доллары наконец распознаются, предупреждение в
   тексте справочника стало отказом с путём до блока.

### 17.4. Устройство

```
авторский текст ──inline.py──> Text(..., Math(latex, display), ...)
                                        │
                      emit/html.py ─────┤──> "$…$" — как сегодня, байт в байт
                                        │
                      emit/docx/ ───────┴──> omml.py: LaTeX -> дерево -> m:oMath
```

`layout.Math(latex: str, display: bool)` — инлайн-элемент, обещанный §5.
Несёт **сырой LaTeX**, как `Run` несёт сырой текст: разбирает и эскейпит
бэкенд. Поэтому `Math` попадает всюду, где сегодня работает `Text`, — в
условие, вариант теста, утверждение, ячейку таблицы, ответ, пояснение, — и
ни один вид задания об этом ничего не узнаёт.

`inline.py` получает третий распознаваемый токен рядом с `<sup>/<sub>` и
прогоном подчёркиваний. Правило пары: `$$…$$` ищется раньше `$…$`, оба — в
пределах одной строки; незакрытый доллар остаётся текстом. Внутрь формулы
разбор не заглядывает: подчёркивания там принадлежат LaTeX.

`omml.py` — два шага, как в любом конвертере:

```python
parse(latex) -> Node | None        # Row, Frac, Rad, Sup, Sub, SupSub, Sym, Text
omml(node)   -> str                # m:f, m:rad, m:sSup, m:sSub, m:sSubSup, m:r
```

`parse` возвращает `None` там, где встретил незнакомое, и называет, что
именно, — это и есть текст записи в отчёте. Никаких исключений: непонятая
формула не должна ронять сборку листа, у которого всё остальное в порядке.

Пространство имён `xmlns:m` добавляется в `_NAMESPACES` рядом с `w`, `wp`,
`a`, `wpg`, `wps`. Порядок детей в OMML — такая же последовательность схемы,
как `w:pPr`: перепутанный порядок Word не прощает и не объясняет, поэтому
конструкторы собирают элементы сами, а не из словаря вызывающего.

### 17.5. Подмножество

| LaTeX | OMML | замечание |
|---|---|---|
| `\frac{a}{b}` | `m:f` (`m:num`, `m:den`) | самый частый случай и причина фазы |
| `\sqrt{x}`, `\sqrt[n]{x}` | `m:rad` (без степени — `m:degHide`) | |
| `x^{2}`, `x^2` | `m:sSup` | без скобок берётся один символ — как в TeX |
| `x_{0}`, `x_0` | `m:sSub` | |
| `x_0^2` | `m:sSubSup` | порядок написания любой |
| `\alpha`…`\omega`, `\Delta`, `\upsilon` | символ Unicode | таблица уже есть — `references/symbols.md` |
| `\cdot`, `\times`, `\pm`, `\approx`, `\neq`, `\le`, `\ge`, `\to`, `\infty`, `\propto`, `\circ` | символ Unicode | те же знаки, что справочник советует писать прямо текстом |
| `\left(…\right)` и обычные скобки | `m:d` | скобка растёт по содержимому — ради этого и нужен `m:d`, а не два символа |
| `\text{…}`, `\mathrm{…}` | `m:r` с `m:nor` | прямое начертание: единицы измерения и русские слова внутри формулы |
| `\,` `\;` и экранированный пробел | узкий пробел | |
| буква вне `\text` | `m:r`, курсив по умолчанию OMML | переменная выглядит переменной без нашего участия |

Вне подмножества — и это осознанно: `\int`, `\sum` и `\prod` с пределами
(`m:nary`), матрицы и окружения `\begin{…}`, `\overline`, `\vec`, `\hat`,
цвета, размеры, макросы. Каждое из них — отдельный узел OMML и отдельная
строка в таблице; заводить их до того, как учитель прислал такую задачу,
значит писать код под воображаемый лист.

### 17.6. Отчёт вместо тишины

Формула, которую парсер не понял, печатается исходным текстом — вместе с
долларами, иначе учитель не поймёт, что это было, — а сборка говорит:

```
Формулы, которые Word не понял (вставлены текстом):
  задание 4: $\int_0^t \upsilon\,dt$ — неизвестная команда \int
```

Три требования к сообщению: назвать формулу целиком (искать её по листу
учитель не должен), назвать **что именно** непонятно, назвать место — номер
задания эмиттер знает из `Numbered`, и этого достаточно; идти за `id` блока
через слой вёрстки ради этого не нужно.

Сообщение читает и модель: по нему она должна суметь переписать формулу
проще, а не «попробовать ещё раз то же самое». Значит формулировка — русская
и конкретная, как все остальные сообщения скилла.

### 17.7. HTML обязан не измениться

Это главный инвариант фазы, и проверяется он тем же способом, что в Ф1:
существующие эталоны не перегенерируются. Механика: `emit/html.py` печатает
`Math` как `esc("$" + latex + "$")` — ту же строку и с тем же эскейпингом,
которую сегодня печатает `Run`. Единственный способ это сломать —
«улучшить заодно»: нормализовать пробелы, развернуть `\alpha` в `α`. Не
делать; правки вывода HTML — отдельные коммиты после фазы, как и в Ф1.

### 17.8. Порядок работы

1. `layout.Math` и распознавание долларов в `inline.py`; HTML печатает
   по-старому. Прогнать эталоны: **байт в байт**. Word на этом шаге
   печатает формулу текстом — ровно как сегодня, регрессии нет.
2. `omml.py`: каркас — `m:oMath` с одним прогоном `x` и `xmlns:m`. Вставить
   в документ, открыть в Word. Пока не открывается, дальше не идти — тот же
   первый шаг, что в Ф2 и Ф3, и по той же причине.
3. Парсер: атомы, группы `{…}`, `^` и `_`. Тесты на дереве, без XML.
4. `\frac`, `\sqrt`, скобки `m:d`.
5. Таблица символов: греческие буквы и операторы.
6. `\text{…}` и пробелы.
7. `$$…$$` — `m:oMathPara` отдельным абзацем.
8. Отказ и отчёт: `parse` возвращает причину, `build_docx` отдаёт записи,
   CLI печатает.
9. Справочники: строка в `symbols.md` о том, что переживает Word, и — если
   решение 2 из 17.3 принято — ошибка на пропуск внутри формулы.
10. `evals/word.md`: раздел «Формулы».

### 17.9. Проверки

| что | как |
|---|---|
| HTML не изменился | существующие эталоны документа — байт в байт |
| каждая конструкция подмножества | табличный тест: LaTeX → ожидаемый фрагмент OMML, по строке на строку таблицы 17.5 |
| разбор | тесты на дереве: `x^2`, `x^{10}`, `x_0^2`, вложенные дроби, `\sqrt[3]{x}` |
| вне подмножества | текст сохранён дословно, ровно одна запись в отчёте, сборка успешна |
| формула доезжает отовсюду | конформанс: формула в условии, в варианте, в ячейке таблицы, в ответе — везде `m:oMath` |
| Word открывает | `python-docx` и `evals/word.md`: формула выделяется как объект и правится редактором формул |
| детерминизм | две сборки байт в байт |
| эскейпинг | `&<>` внутри `\text{}` и в теле формулы; непарный `$`; пустая формула |
| эталон | `mixed.docx.xml` дополняется блоком с дробью — диф формулы читается глазами |

### 17.10. Риски

| риск | что делаем |
|---|---|
| парсер разрастётся в «ещё чуть-чуть LaTeX» | подмножество — таблица в коде; новая команда = строка таблицы плюс тест плюс строка в справочнике, иначе не добавляется |
| Word молча отказывается из-за порядка детей в OMML | шаг 2 отдельно и до всего остального; конструкторы собирают порядок сами |
| формула понята неправильно (`x^23` как `x²3`) | это правило TeX, а не баг: тест его фиксирует, справочник советует скобки |
| `Cambria Math` нет в системе | Word подставит замену, формула останется формулой; проверяется глазами на чек-листе |
| KaTeX и OMML выглядят по-разному | принимается: два формата — две типографики. Лист остаётся читаемым в обоих, а совпадения по пикселям мы никогда не обещали |
| соблазн «заодно» поправить HTML | правки вывода HTML — отдельные коммиты после фазы |

### 17.11. Чего не делаем

- **Не вендорим KaTeX и не расширяем его конфиг.** Компромисс из «Известных
  компромиссов» остаётся: формулы в HTML требуют интернета.
- **Не заводим тип блока «формула».** Формула живёт внутри текста, как и
  сегодня; отдельный блок означал бы вторую запись одного и того же.
- **Не переводим формулы в картинки.** Ни в HTML, ни в Word: это потеря
  правки, ради которой формат и заводился.
- **Не поддерживаем LaTeX в подписях иллюстраций.** Подпись — часть рисунка,
  её словарь — Unicode и `<sup>`/`<sub>`.

### 17.12. Что разошлось с планом

**Граница модуля называется `convert`, а не `parse`.** План обещал, что
`parse` вернёт `None` с причиной. Разбор и отказ оказались разными вещами:
`parse` строит дерево и бросает `Unknown`, называя команду, а `convert`
ловит его и отдаёт паре `(OMML или None, причина)`. Внутри — исключение,
наружу — пара; сборка листа от непонятой формулы не падает, как и обещано.

**Скобки различают структуру и знак.** План писал «`(…)` → `m:d`». На деле
`(0; 5]` — это диапазон, а не сломанная формула, поэтому круглая или
квадратная скобка становится растущей `m:d` только если у неё есть пара;
непарная остаётся обычным символом. Структурной осталась одна фигурная:
незакрытая `{` — это формула, которую мы не поняли, и угадывать, где она
кончается, нельзя.

**Прямой текст не берёт математический шрифт.** `\text{м/с}` печатается
шрифтом документа, а не Cambria Math: единицы измерения внутри формулы
должны читаться как соседнее предложение. `m:nor` и отсутствие `w:rFonts` —
это одно решение, а не два.

**Нашлась чужая ошибка.** Пока искали место для формулы в эмиттере,
выяснилось, что рамка для колонки и для секции «Ответы» собиралась заново
вместе со счётчиком рисунков: лист с картинкой в `row` получал два
`wp:docPr id="1"`. Починено отдельным коммитом до фазы — Ф5 тут ни при чём,
но найти это иначе было бы нечем.

**Отчёт называет задание, а не блок.** Плана хватило: номер задания эмиттер
знает из `Numbered` и несёт в рамке. Идти за `id` блока через слой вёрстки
не понадобилось, и хорошо — это протащило бы имя файла черновика в бэкенд.
