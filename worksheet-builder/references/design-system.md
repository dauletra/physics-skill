# Дизайн-система рабочего листа

Это справочник для человека и для `scripts/assets.py` (в нём — `BASE_CSS`),
которая держит все эти константы в CSS. Ты (Claude) обычно **не должен** ничего здесь
редактировать вручную во время создания рабочего листа — правь `tasks/*.json`,
а не HTML/CSS. Меняй этот файл и синхронно код рендерера, только если учитель
явно просит изменить визуальный стиль всех будущих листов (например, «сделай
шрифт крупнее для 5 класса»).

## Страница и печать

- Формат: A4, портретная ориентация
- Поля по умолчанию: 15mm сверху/справа/снизу, 18mm слева (запас под
  подшивку/скрепление) — это именно пресет "По умолчанию", учитель может
  переключить на "Нет"/"Минимум" прямо в браузере, см. "Поля печати (верхняя
  панель)" в "## Page-view" ниже
- `@page { size: A4; margin: ... }` + `@media print` — обязательный блок в каждом
  сгенерированном HTML; значение `margin` не статично — переписывается на
  лету через CSSOM при смене пресета полей (см. ниже)
- Разбивка страниц: у каждого блока задания `break-inside: avoid` — задание не
  должно разрываться между страницами, если влезает целиком; если не влезает,
  подпись "продолжение на след. странице" не требуется — просто переносится целиком
- На экране разбивка по страницам видна ещё до печати — см. "## Page-view"
  ниже

## Типографика

- Шрифт: `"PT Sans", "Segoe UI", Verdana, Arial, sans-serif` — гарантированная
  поддержка кириллицы даже без PT Sans (запасной стек — системные шрифты)
- Базовый размер текста: 12pt, интерлиньяж 1.4
- Заголовок листа (`title` из meta.json): 16pt, bold
- Текст задания: 12pt normal
- Подписи/мелкий текст (баллы): 9pt

## Фон

Страница — абсолютно белая (`background: #fff` на `html` и `body`), без
серого/кремового оттенка от системной темы браузера. Единственное, что не
подчиняется этому — узкая штриховка внутри `.answer-block` (визуальный акцент
блока с ответом), она не влияет на фон всей страницы.

## Цвет — только для экрана, не для печати

Раз печать чёрно-белая, все смысловые различия задаются **формой**, а не цветом:
пунктир/штрихпунктир для графиков, рамки/заливка-штриховка для акцентов, жирность
для номеров заданий. Цвет можно использовать только как декоративный акцент,
который не несёт уникальной информации (то есть лист обязан быть полностью
читаем, даже если цвет пропадёт).

## Шапка листа

Слева направо/сверху вниз:
1. Строка метаданных для заполнения от руки: `Школа/класс: _____ Дата: _____`
   и `Фамилия Имя: _______________` — рендерер сам рисует прочерки нужной длины,
   даже если `school`/`date` в meta.json пустые. Подписи здесь — из
   `STRINGS["ru"]` (см. "Локализация служебных строк" ниже) — не хардкодь
   текст, если правишь рендерер.
2. Заголовок (`title`), под ним — `subject` + `grade` + суффикс "класс" мелким шрифтом
3. Если есть `instructions` в meta.json — абзац курсивом под заголовком

## Нумерация заданий

- Сквозная нумерация начиная с 1, порядок берётся из `meta.json → order`, а не
  из имени файла
- Номер — просто жирная цифра с точкой (`1.`), без рамки или фона, сразу за
  ним на той же строке идёт текст задания (перенос на вторую строку — под
  текстом, а не под номером); одинаково для всех типов заданий — тип задания
  не меняет номер, только форму содержимого под ним
- Если у задания есть `points`, баллы показываются мелким текстом сразу
  **после текста задания** (`... до конца строки. (2 б.)`), а не рядом с
  номером — номер должен предварять сам текст, а не оценку. Суффикс "б." —
  из `STRINGS[lang]["points_suffix"]`, не литерал в разметке.
- Задание — это список компонентов (`components`), не один монолитный тип
  (см. `task-schema.md`). Буквы `a)`, `b)`... получают только *отвечаемые*
  компоненты, и только если их в задании больше одного — с небольшим отступом
  от общего условия (`.task-component-lettered`), та же логика "буква + текст
  пункта, баллы пункта после текста" действует и для них — независимо от
  баллов всего задания. Информационные компоненты (текст, график, таблица...)
  букв никогда не получают.

## Раскладка компонентов: `layout`

По умолчанию компоненты задания идут один под другим на всю ширину. Task-level
поле `layout` (см. `task-schema.md`) партиционирует список компонентов на
строки — например `[1, 2]`: первый компонент на всю ширину, следующие два —
50/50 в одной строке. Ширина строки — либо N равных колонок (целое число),
либо явные проценты на строку (`[40, 60]`).

Это заменяет прежнюю жёсткую пару "текст слева / один визуал справа" —
`chart`/`illustration` больше не получают собственный двухколоночный layout
по умолчанию только потому что они `chart`/`illustration`; вместо этого автор
JSON явно решает через `layout`, что с чем стоит рядом (например, дан график —
в одной строке, а следующие два вопроса по нему — в следующей строке 50/50).

**Но:** SVG-генераторы графиков/схем (`build_chart_svg`, `SVG_SNIPPETS` в
`scripts/visuals.py`) откалиброваны под колонку ~36% ширины (шрифты, толщина линий, `viewBox` — см.
`charts-and-graphs.md`) — при более узкой строке (например, три колонки по
~33%) картинка не сломается (это тот же SVG, отмасштабированный уже), но
пропорции текста внутри неё калибровались не под такую ширину, так что
читаемость на непроверенных пропорциях стоит проверить визуально, а не
считать по умолчанию корректной.

## Верно/неверно — зебра-полоски

Строки `.tf-row` в `list` с `item_style: "statement_bool"` чередуют белый фон
и `#f2f2f2` (`nth-child(even)`) без зазоров между строками — это помогает
визуально не потерять, какому утверждению соответствует какая пара
"Верно/Неверно" в длинном списке. Правило статическое (не переключается) —
двух состояний тут нет, только чередование.

## Интерактивные элементы вёрстки в браузере

Это про мини-тулбары *внутри конкретного задания* (`CONTROL_GROUPS`). Про
отдельную, одну на весь документ панель наверху страницы (поля печати и
другие инструменты уровня всего листа) — см. "Поля печати (верхняя панель)"
в разделе "Page-view" ниже.

Часть компонентов (`prompt_response` с `response: "lines:N"`, `list` с
`item_style: "choice"`) печатают рядом с собой пустой
`<div class="layout-toolbar" data-controls="...">`. JS-код в
конце сгенерированного HTML (`LAYOUT_JS` в `scripts/assets.py`) наполняет его
кнопками и переключает CSS-классы у нужного элемента внутри того же блока —
всё **только в браузере, без перезапуска рендерера**. Тулбар виден исключительно
на экране: `@media print { .layout-toolbar { display: none !important; } }`
скрывает его при печати, а выбранное состояние — это состояние DOM на момент
печати (Ctrl+P), т.е. если учитель переключил "опустить вниз" и жмёт печать —
печатается именно так. При повторной генерации из JSON тулбар возвращается к
дефолту, заданному в JSON (или к дефолту рендерера, если поле не указано) —
если нужно, чтобы выбор пережил пересборку, его стоит сохранить в
соответствующее поле JSON (`layout`, `show_solution`, `variants_layout`), а не
полагаться только на клики в браузере.

Тулбар-скрипт помечает уже построенный тулбар (`toolbar.dataset.built`) и
пропускает его при повторном запуске — это специально для сценария "открыл
готовый HTML в браузере → сохранил через Ctrl+S/'Сохранить как' → открыл
сохранённую копию снова": браузер сериализует текущий DOM (уже с построенными
кнопками), и без этой защиты скрипт при повторном открытии дописывал бы
кнопки ещё раз поверх старых (что и производило задвоение при каждом цикле
открыл-сохранил). Сам CSS-класс раскладки (ширина/положение/видимость) при
таком сохранении переживает браузер нормально — ломался только билдер
тулбара. **Важно:** такая пересохранённая копия — это тупиковая ветка, не
известная рендереру; если учитель потом снова обратится к Claude с правкой
содержимого этого же листа, скрипт перегенерирует HTML заново из JSON и
тулбар-правки, сделанные вручную в браузере, потеряются — если раскладку
нужно сохранить насовсем, её стоит проговорить с Claude и записать в
соответствующее поле JSON, а не полагаться только на пересохранённый файл.

Сейчас доступны:
- **`prompt_response` (`response: "lines:N"`)** — "Место для решения" (показать/скрыть).
- **`list` (`item_style: "choice"`)** — "Варианты" (1 колонка / 2 колонки / в строку).

Чтобы добавить новый переключатель для любой формы компонента (существующей
или будущей) — четыре шага, без изменения остального кода:
1. В `scripts/components.py` добавить условие в `render_layout_toolbar(comp)`
   (принимает весь компонент, не только `type` — так можно различать формы
   внутри одного формата, например `item_style` у `list`), возвращающее
   нужный ключ группы (через запятую, если групп несколько).
2. Убедиться, что HTML этой формы содержит элемент с классом, за который
   можно зацепиться (например, свой `.mc-options`-подобный контейнер).
3. Добавить запись в JS-объект `CONTROL_GROUPS` внутри `LAYOUT_JS`: подпись,
   CSS-селектор цели (`target`), тип переключения (`radio` через
   классы-префиксы или `toggle-visibility` через `display`) и список
   пресетов.
4. Если подпись — новый фиксированный текст (не число/процент), добавить её
   в `UI_STRINGS` вместо литерала прямо в `CONTROL_GROUPS` — см.
   "Локализация служебных строк" ниже.

### Раскладка компонентов — per-row кнопки колонок

Отдельный от `CONTROL_GROUPS` механизм (не radio/toggle-visibility класс на
готовом элементе, а перестройка DOM), потому что раскладка `.task-row`/
`.task-col` — это структура, а не одно переключаемое CSS-состояние. Любое
задание, где `.task-components` в итоге содержит больше одного `.task-col`,
получает на каждой строке (`.task-row`) hover-only оверлей `.row-controls` с
двумя кнопками-иконками ("+"/"-", SVG из Lucide, скопированы один раз как
строки в `ROW_ICONS` — без npm-зависимости).

Шапка задания (номер + `prompt`, `render_header_line` в `render_task()`) для
этого механизма — тоже колонка: если задание не свёрнуто в
"один вопрос без вступления" (`single_component`), она рендерится как
`.task-row > .task-col` строки 0 `.task-components`, а не отдельным элементом
вне неё, — именно поэтому её тоже можно смёрстить с первой строкой реальных
компонентов через "+". `layout` из JSON эту строку не считает (партиционирует
только `components`), она всегда добавляется поверх как отдельная стартовая
строка.

- `initRowControls()` при `DOMContentLoaded` для каждого `.task-components`
  считает текущие `.task-row`/`.task-col` (строго через `:scope > .task-row
  > .task-col`, не `row.children` — иначе сам `.row-controls`-оверлей
  посчитался бы лишней колонкой) и строит из них массив ширин `widths`
  (например `[1,2,1]`) плюс плоский упорядоченный список узлов `.task-col`
  — этот список узлов переиспользуется при каждой перестройке, компоненты не
  клонируются и не теряют своё содержимое/под-тулбары.
- "+" на строке `i`: `widths[i]++`, `widths[i+1]--` (строка `i+1` удаляется
  из массива, если стала пустой) — забирает первый компонент следующей
  строки как новую колонку текущей. Задизейблена на последней строке.
- "-" на строке `i`: `widths[i]--`, `widths.push(1)` — убирает последний
  компонент текущей строки; поскольку ширины всех промежуточных строк не
  меняются, состав каждой из них сдвигается на один компонент вперёд (каскад
  получается сам, без явного цикла), а самый последний компонент задания
  оказывается один в новой строке в конце документа. Задизейблена, если в
  строке всего 1 колонка (иначе единственный компонент "перепрыгнул" бы в
  конец, ломая порядок).
- После любого клика — `rebuildTaskRows()` полностью пересобирает
  `.task-components` из `widths` и списка узлов (не точечная правка соседних
  строк), пересчитывая проценты колонок поровну (`100/width`). Кастомные
  проценты из JSON (`layout: [[40, 60]]`) сохраняются только до первого
  клика по "+"/"-" в этом задании — тот же принцип "экран на момент печати",
  что и у `CONTROL_GROUPS`-тулбаров выше.
- Подсветка строки и появление кнопок — чистый CSS (`.task-row:hover
  .row-controls`), без JS mouseenter/mouseleave; `.row-controls` дополнительно
  форсированно скрыт в `@media print` (тот же паттерн, что `.layout-toolbar`/
  `.global-toolbar`), не полагаясь только на то, что `:hover` не сработает
  при печати.
- Тот же гвард на переоткрытие, что у `CONTROL_GROUPS`-тулбаров (см. выше):
  `container.dataset.rowControlsBuilt` — без него "Save Page As" → повторное
  открытие задваивало бы `.row-controls` на каждом цикле.

## Локализация служебных строк

Все фиксированные надписи листа (шапка, "Ответ:", "Верно"/"Неверно", подписи
тулбара, суффикс баллов, `<title>`) идут через два синхронных словаря
(сейчас только с ключом `"ru"` — второго языка нет):
- `STRINGS` (Python, `scripts/strings.py`) — для всего, что рендерится на
  сервере (шапка, подписи типов заданий).
- `UI_STRINGS` (JS, внутри `LAYOUT_JS` в `scripts/assets.py`) — для подписей
  интерактивного тулбара, который строится в браузере.

Оба словаря — плоские `{ru: {...}}`, без вложенной логики; при добавлении
новой строки достаточно добавить ключ в оба места (какой из двух — зависит
от того, рендерится строка в Python или в JS-тулбаре, см. четвёртый шаг
рецепта выше). Не хардкодь текст в разметке напрямую.

## Page-view

HTML-версия не печатает номер страницы — вместо этого на экране (не в
печати) содержимое разбивается на отдельные белые листы размера A4 на
сером фоне (как непрерывный page-view в Google Docs/Word): сколько листов —
столько и будет напечатанных страниц, видно сразу, никаких подписей "стр. N"
не нужно.

- И `body` (случай "всё влезает на одну страницу"), и `.a4-page` (каждый лист
  при разбивке) — это полноразмерный лист A4 (`width: 210mm`), с настоящим
  полем-отступом текста от края (`padding: var(--page-margin)`, CSS-переменная
  из `:root`, по умолчанию равная `@page`'s `15mm 15mm 15mm 18mm` — см.
  "Поля печати (верхняя панель)" ниже про то, как она меняется), а не голая
  ширина текстовой колонки. Именно поэтому текст на экране не упирается в
  серую границу, а стоит с ровным белым полем вокруг — как в Google Docs/Word,
  а не "текст встык с краем". Реальная ширина текста внутри при этом —
  `177mm` (`210 − 18 − 15`) при полях по умолчанию, та же, что и при печати.
- Ни у `body`, ни у `.a4-page` нет запасного `max-width`/сужения под узкое
  окно браузера: ширина всегда ровно `210mm`, при более узком окне просто
  появляется горизонтальная прокрутка. Это принципиально — иначе при сужении
  окна текст переносился бы на другую ширину, чем при печати, и разбивка на
  страницы, посчитанная на экране, могла бы не совпасть с реальной печатной.
- Реализовано в `LAYOUT_JS` (`scripts/assets.py`): функция `paginate()`
  меряет реальную высоту каждого `.sheet-header`/`.task` в px, набирает их
  в группы по `(297 − верх − низ)mm`, где верх/низ — поля активного пресета
  из "Поля печати" (не жёсткая константа — при переключении пресета бюджет
  высоты страницы пересчитывается вместе с остальным), и оборачивает каждую
  группу в `div.a4-page`. Пересчитывается при загрузке, после подгрузки
  шрифтов (`document.fonts.ready`, из-за возможного сдвига высоты после смены
  шрифта KaTeX), при resize, после переключения любого элемента тулбара
  (влияет на высоту задания) и после смены пресета полей печати.
- Если всё влезает на одну страницу, обёртки `.a4-page` не создаются вообще
  — короткий лист выглядит как обычно, без серого фона и теней (просто один
  белый лист `body` с полями).
- В `@media print` у `.a4-page` (и у `body`) `padding`/`width`/тень
  обнуляются — реальные поля страницы при печати даёт только `@page`, чтобы
  поле не задваивалось; вычисленные на экране границы страниц применяются как
  настоящий `break-after: page` — то есть напечатанный результат
  гарантированно совпадает по количеству страниц с тем, что было видно на
  экране, а не просто похож на него.

### Поля печати (верхняя панель)

Отдельная (не привязанная ни к одному заданию) панель `.global-toolbar`
вверху документа — переключатель полей страницы с теми же тремя пресетами,
что в выпадающем списке полей диалога печати Chrome: "По умолчанию" / "Нет" /
"Минимум". Реализация — `PRINT_MARGIN_PRESETS` + `applyMarginPreset()` в
`LAYOUT_JS`.

- Выбор пресета одновременно переписывает и CSS-переменную `--page-margin`
  (даёт видимый на экране эффект), и сам живой `@page`-правило через CSSOM
  (`CSSPageRule.style.margin`, ищется хелпером `findPageRule()`). Из-за этого
  печать с оставленным как есть диалогом Chrome (поля = "По умолчанию" — это
  и так его собственное состояние по умолчанию) **всегда** совпадает с тем,
  что выбрано у нас на экране, каким бы из трёх пресетов он ни был — учителю
  не нужно отдельно трогать поля в самом диалоге печати Chrome.
- **"Минимум" — наше приближение, не гарантированное число Chrome.**
  "По умолчанию" и "Нет" у Chrome — детерминированные величины (первое — то,
  что задано в `@page`, второе — буквально 0), а вот "Минимум" Chrome берёт
  из драйвера/возможностей выбранного принтера — единой зашитой константы
  для этого пресета нет ни в одном официальном источнике (проверялось
  целенаправленно, не проигнорировано). Поэтому наш `minimum: {top: 5,
  right: 5, bottom: 5, left: 8}` — это своё небольшое, но не подтверждённое
  как совпадающее с конкретным принтером учителя значение (тот же +3mm слева
  под подшивку, что и в "По умолчанию", просто в меньшем масштабе).
- Расширяемость — специально ради этого просили сделать так: чтобы добавить
  ещё один инструмент уровня всего листа (не про поля печати, а что угодно
  другое), достаточно дописать новый объект в массив `GLOBAL_TOOLBAR_TOOLS`
  (`label`/`options`/`onSelect`) — сам рендер (`buildGlobalToolbar()`) один
  на все инструменты и трогать его не нужно. Это отдельный, самостоятельный
  массив от `CONTROL_GROUPS` — тот про мини-тулбары *внутри* конкретных
  заданий (см. "Интерактивные элементы вёрстки" выше), этот — про панель
  уровня всего листа, один раз наверху документа.
- Про сам диалог печати Chrome: `@page { margin: ... }` уже читается им как
  поля при настройке "По умолчанию" в выпадающем списке полей — именно
  поэтому переключение пресета переписывает `@page`, а не просто CSS на
  экране. Отдельная от этого настройка — включённая по умолчанию галочка
  "Заголовки и нижние колонтитулы" в диалоге печати: это состояние самого
  браузера, из HTML/CSS её не убрать; см. `SKILL.md` про предупреждение
  учителю.

## Версия для учителя vs ученика

Рендерер собирает оба файла из одних и тех же `tasks/*.json` — учитель не должен
вести два источника правды:
- Студенческая версия: скрывает все поля `answer`/`answer_map`/`answers`/`blanks`-значения, показывает пустые места для решения/ответа
- Учительская версия: показывает те же блоки заданий, но с ответами, выделенными
  визуально (например, рамка с пометкой "Ответ:") сразу под условием — без
  необходимости листать отдельный ключ ответов в конце
